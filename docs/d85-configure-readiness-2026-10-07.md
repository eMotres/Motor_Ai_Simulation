## Finding

The D85 L13 v1 passport file already exists in shared production data at `/srv/motres/shared/passports/CIANO28 85 20SW1200/L13.json` (about 83 KB, dated Oct 6; production inventory reported by the orchestrator). Its copied counterpart is [shared_L13.json](../scratch_s1_20261006/d85_finish_20261007/shared_L13.json). It identifies schema `passport-v1-full-1`, machine `CIANO28 85 20SW1200` / `L13`, and has three PWM variants (Si 48 kHz, GaN 48 kHz, GaN 100 kHz), each covering 20 points over 250–2000 rpm and 6.47–45.96 A RMS.

The newer production integration is present in [production_catalog.py](../scratch_s1_20261006/d85_finish_20261007/production_catalog.py) and [passport_store.py](../scratch_s1_20261006/source/src/motor_ai_sim/passport_store.py). `/api/catalog` attaches `pwm_variants` from the versioned store to a matching existing catalogue passport. `/api/catalog/references` returns the lean Configure reference feed, likewise attaching the variants. The store is read-only: it matches the v1 file to a catalogue card by `"<die> <config>"` name, or a die-only name plus exact base stack length, and supplies usable PWM variants and full-card date metadata. It deliberately does not replace or create the card's base analytical 2D passport.

The fetched effective shared catalogue does contain one legacy D85 base card, `cat_ciano28_85` (`CIANO28 85`, preset `ciano28_85_13`). It has a populated legacy analytical passport, `fit`, and `geo`, but it is not the L13 geometry in the v1 snapshot. The card geometry is OR 42.5, IR 33.1, rotor OR 32.8, rotor IR 24.3, 24 slots/28 poles, magnet height 7.7 mm; its fit values are slot height 7.0, insulation 0.05, wire spacing 0.12, slot width 3.3, wire width 3.0 mm. The L13 snapshot is OR 42.5, IR 32.7, rotor OR 32.4, rotor IR 24.6, 24 slots/28 poles, magnet height 7.0 mm; fit is 7.4, 0.05, 0.07, 3.8, 3.5 mm. Thus the existing card passes the outer-radius and slot/pole checks but fails Configure's magnet-height tolerance (0.7 mm difference against a 0.3 mm limit). Its `N0=13`, `L0=13 mm`, and `wireH0=0.4 mm` also do not identify the snapshot's 0.3 mm wire build. Do not present this existing base passport as the L13 reference.

The base card does contain nonempty analytical current, speed, and loss-grid data. The issue is its stale/mismatched geometry and identity, rather than a missing legacy wrapper. The shared v1 file's `source` points to `docs/data/passport_d85/passport_L13.json`; the supplied `shared_L13.json` itself contains only `schema`, `machine`, `source`, and `pwm_variants`, not the Configure base wrapper.

## Expected publication mapping

The product shell is tab-based, not a literal `/motor` pathname. The visible path is **Motors → CIANO28 85 20SW1200 → L13** in the family hierarchy, then **Configure** (tab id `compare`). For Configure to select this passport automatically, it must be exposed through the catalogue reference feed consumed by `fetchCatalogReferences()`.

The legacy catalogue-backed Configure contract is:

```json
{
  "id": "<stable catalog motor id>",
  "name": "CIANO28 85 20SW1200 · L13",
  "diameter_mm": 85,
  "preset": "<preset that resolves to the same L13 geometry/build>",
  "passport": {
    "passport": { "N0": 0, "L0_mm": 0, "wireH0_mm": 0, "I0_A": 0,
      "rpm0": 0, "nP0": 0, "T0_Nm": 0, "Vemf0_peak_V": 0,
      "R0_ohm": 0, "endWindFrac": 0, "Pfe0_W": 0,
      "Pmag0_W": 0, "mass0_kg": 0, "speed": {"rpm": [], "Pfe_W": [], "Pmag_W": []} },
    "fit": { "slotHeight_mm": 0, "insulation_mm": 0,
      "wireSpacingY_mm": 0, "slotWidth_mm": 0, "wireWidth_mm": 0 },
    "geo": { "statorOR_mm": 42.5, "statorIR_mm": 0,
      "rotorOR_mm": 0, "rotorIR_mm": 0, "numSlots": 24,
      "numPoles": 28, "magnetHeight_mm": 0 },
    "slots": 24,
    "poles": 28
  }
}
```

Zeroes above mark required field names only; they are not publishable motor values. `statorOR_mm` is a radius in this interface, so an 85 mm stator OD maps to **42.5 mm**, not 85. The other `geo` and `fit` values must come from the exact L13 snapshot. The underlying `passport` must provide real measured values. Keep provenance, convergence/acceptance flags, and measured coverage alongside the UI payload; do not convert unresolved fields to guessed values.

The base wrapper is stored on `motor_catalog.json` card field `motor.passport`; the legacy generator returns `{passport, fit, geo, poles, slots}` in [passport.py](../src/motor_ai_sim/passport.py). Production source keeps a `POST /api/catalog/{motor_id}/passport` generation route, and `GET /api/catalog/{motor_id}/passport` returns the stored card. Neither route is the v1 variant importer: [export_passport_store.py](../scratch_s1_20261006/source/scripts/export_passport_store.py) emits only identity and PWM variants, and the v1 card assembler creates a different full-record schema. Production reference sources are caller workspace catalog first, then shared `motor_catalog.json` when layered workspaces are enabled. A workspace card with the same stable id takes precedence even if it has no passport, so it can shadow the shared D85 card.

## Why a loaded D85 may not auto-select

Configure's reference mapper requires the base wrapper: the production frontend tries `/api/catalog/references` first (then falls back to `/api/catalog`) and skips cards without `passport.passport`, `passport.fit`, or `passport.geo`; see the read-only [production referencePassports.ts](../scratch_s1_20261006/source/web/src/lib/referencePassports.ts). It then matches slots/poles, stator outer radius within 0.5 mm, and magnet height within 0.3 mm. The current shared card has the required wrapper and matches slots/poles and OR, but its magnet-height difference is 0.7 mm, so it is rejected for the L13 geometry. Same-section candidates are ranked by L0, wire rows and wire height; the loaded machine's catalog membership is a later tie-breaker, not a hard filter. The v1 record has exact geometry/fit in its source snapshot, but its slim shared store file contains neither these fields nor the legacy base analytical model.

The production store reads `<shared>/passports/<die>/<config>.json`; `_records()` indexes each JSON filename as the configuration. `_pick()` requires the catalogue card name to equal either `CIANO28 85 20SW1200 L13` or exactly the die name `CIANO28 85 20SW1200` (the latter is only unambiguous when a single config exists, otherwise exact stack length is required). The supplied shared record is named correctly for the intended die/config, but the current catalogue card name is only `CIANO28 85`; it matches neither accepted name, so its PWM variants and card metadata do not attach to this card. A workspace card with a duplicate id may also shadow the shared catalogue card before passport filtering.

Correcting the catalogue name would make that shared PWM record attach, so it must be reviewed before any such publication. The fetched variants have `motor_pwm_loss_W: null` and no motor-PWM anchor; they must not be presented as a qualified motor PWM comparison. The new candidate harness runs `pwm="off"` and emits no `pwm_variants`; publication must continue to withhold these store variants or label their incomplete basis truthfully.

Reference visibility follows the production catalogue rules: non-admins do not see private cards they do not own; when their access is grant-limited, `_grant_visible_cards()` also requires the card name to resolve to a die/config in their visible die index and to be covered by their grant. `/api/catalog/references` applies the same visibility filters as `/api/catalog`. Its `has_machine` flag is computed from caller-visible die/config names and only breaks ties after build and geometry closeness. Thus an absent reference can mean the base card is absent, shadowed, private, or outside the caller's die grant; presence of the shared v1 JSON alone does not prove it reaches that caller.

The v1 scripts and production catalogue source are newer than the local checkout. The checked-in [local referencePassports.ts](../web/src/lib/referencePassports.ts) still fetches only `/api/catalog`, while the supplied production frontend source tries `/api/catalog/references` first and understands the attached `pwm_variants`, `has_machine`, and `card` fields. The source snapshot has no v1-to-legacy catalogue wrapper builder: `passport_pilot.py assemble` calls `passport_v1.card.build_record()` to emit a v1 record, and `export_passport_store.py` only exports PWM data. The exact code5 legacy `generate_passport()` can produce the required wrapper, but it runs FEM and must use the exact L13 geometry/build. The smallest safe publication step is therefore to create/validate an explicit wrapper for the L13 build (with real analytical values and exact `geo`/`fit` from its frozen snapshot), attach it to a catalogue card with an accepted exact die/config name, and then verify reference visibility and matching in a fixture. Do not copy the existing `cat_ciano28_85` geometry onto L13 or infer values from the shortened card name. Do not use the stale local checkout generator; the isolated harness below targets the fetched code5 source.

## Qualification limits before publication

The data is broad enough to support a measured Configure reference, but its displayed limits must not imply more validation than the records provide. The v1 shared file’s PWM coverage is 20 points per variant over 250, 500, 1000, 1500, and 2000 rpm and 6.47, 12.94, 25.88, and 45.96 A RMS. `state_L13.json` calls 6.47 A a **provisional** demagnetization cap; it is not a verified safe current limit. The D85 result notes [d85-live-result-status-2026-10-06.md](d85-live-result-status-2026-10-06.md) report the earlier 48 kHz PWM point at 4 samples/carrier with `demag_settled=false` and `eddy_settled=null`, and a failed continuous-rating verification with the magnet at 156.1 °C against a 150 °C limit. The separate 150 °C demag comparison settled, but carried a 1.02% per-magnet spread and sparse cogging sampling; it does not repair the PWM result’s flags. Preserve these as provenance/qualification constraints and do not advertise the provisional limit or an unverified S1 rating as qualified.

## Isolated wrapper completion harness

[run_configure_reference.py](../scratch_s1_20261006/d85_finish_20261007/run_configure_reference.py) wraps the unchanged code5 legacy `generate_passport()` in a no-publication runner. It requires the isolated `/work/code5`, `/work/ws_configure/motor_config.yaml` (a private copy of `ws_L13`), `/work/shared`, and copied snapshot/state inputs. It refuses to write into `ws_L13` and only writes under `/work/out/configure_reference`; it never uses HTTP or a catalogue route. Its `--preflight-only` mode imports the production route and runs only the exact results-ledger probe; it cannot start FEM. Full generation reuses an existing result only after the solver's canonical key probe and an affirmed `ledger_hit`.

The runner takes the calibrated d-axis from `state_L13.json`, the hot-loss gamma from the unique 25.88 A / 1000 rpm row in `loss_plan3`, and exact snapshot geometry, materials, mesh, 4S/star connection, battery, and 2.027 end-winding factor. It checks that the shared family die/config YAML resolves to the same geometry, winding, and real material assignments, while preserving the shared L13 rated/peak duties. The saved `parts.shaft: reference` value is retained in the shared file; the solve explicitly passes `included` per the owner's effective-state decision. Because the unchanged generator does not pass magnet/coil temperature arguments itself, the process-local route wrapper supplies the snapshot's 150 °C magnet / 180 °C coil reference to every solve. These are limit-temperature proposal conditions; they are not the non-converged rated-duty temperatures (210.7/293.6 °C), and the 25.88 A point must not be called an S1/continuous rating.

The runner uses `pwm="off"`, writes a standalone reference-feed candidate named exactly `CIANO28 85 20SW1200 L13` with the legacy Configure wrapper, and never attaches the shared v1 PWM variants. It deliberately omits a legacy `preset`: `ciano28_85_13` resolves to the wrong geometry, while machine loading should use the existing family die/config route. It captures hashes for solver/source inputs, exact per-solve requests/status/timing, and computed wrapper fields. Before each route call it flushes a JSONL `solve_started` record; each completed or failed call is appended immediately with request hash and solver source hash. The route's coupled `eddy` option is distinct from `rotor_eddy`: passport generation maps its `eddy` argument to `rotor_eddy` and omits the route-level option, whose default is false. Since the frozen L13 rated duty explicitly saves `eddy_coupled: true`, the harness supplies that exact saved value as route `eddy`, records its setting/source in preflight and per-solve provenance, and refuses a full generation unless an unchanged-source preflight proved the same setting and request plumbing. It stops on the first missing or non-true required verdict (`steady_state`, `qualified`, `nonlinear_converged`, coupled `eddy_settled`, and `demag_settled` when demagnetization was requested), after writing the completed result to JSONL and an unpublished rejection record. Demagnetization is not required when that solve did not request it. `--attempt-id <id>` isolates preflight, checkpoint, rejection, and candidate files under `out/configure_reference/attempt_<id>/`, preserving previous attempts and requiring a preflight from the same attempt with matching input hashes.

The separate 1000 rpm S1 recheck in [s1_recheck_n1000_completed.json](../scratch_s1_20261006/d85_finish_20261007/s1_recheck_n1000_completed.json) ran 1625.324 s and was rejected: thermal verification passed with a -1.6 K miss; nonlinear convergence and eddy settling passed, but after 32/32 demagnetization pre-pass periods `demag_settled=false` and `steady_state=false`. The final-period Br change and rotor-image history passed (`area_mean=2.46e-8`, `element_max=5.50e-6`, 7-cycle history complete). The decisive recorded failure was torque mean relative drift `0.0028214` against the unchanged `0.001` limit; ripple drift `0.05346 pp` was under its `0.19111 pp` limit. The solver requires the Br, image-history, and observable-drift checks together; the recorded image gap is diagnostic and does not substitute for history completeness. No tolerance or physics change is proposed.

Expected call count before early rejection is usually 20–25: two base points, three initial current points, 15 loss-grid points, zero to three demagnetization-knee extensions, and zero to two current refinements. The rated-speed loss grid uses 120 steps; the adaptive current sweep uses 60 from the generator's `max(6, base_steps // 2)` rule. Actual count is recorded, not assumed. The candidate is always marked unpublished and blocked pending solver verdicts, geometry/fit checks, Configure fixture matching, ordinary-user visibility, shared PWM-store review, and parent approval. An unknown or false steady-state verdict prevents the strict qualification flag.

This harness does not launch FEM as part of this audit; the separate S1 result above is from the parent-supervised isolated server run. From a fresh isolated `/work` tree, copy it under `/work/code5/scripts/` and invoke it with the private config, shared directory, frozen inputs, and a unique `--attempt-id`. First use `--preflight-only` to prove import/config/family checks and exact ledger-probe plumbing without FEM; full generation is a separate supervised action. No copied source state under `ws_L13` or `out/full` should be used as an output target.

Production has focused temporary-store/reference tests in the supplied source snapshot: `tests/test_passport_store.py` covers v1 variant matching and attachment; `tests/test_catalog_shared_references.py` covers layered catalog precedence and visibility; `tests/test_catalog_cards_routes.py` covers catalog route access. These can verify routing/visibility/store behavior after a correctly named wrapper fixture is prepared; they do not verify that the current `cat_ciano28_85` matches the L13 geometry or validate a generated solver result. Safe isolated command (run from an isolated writable copy of `scratch_s1_20261006/source`, with no live API):
