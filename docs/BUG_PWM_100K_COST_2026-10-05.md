# 100 kHz PWM FEM: not stuck in meshing — a cost cliff (2026-10-05)

Status: **diagnosed (25 min), not fixed** (owner rule: write it up, don't chase it).
Found by: Ø40 passport stage 3 (PR #106 / feat/passport-d40-pwm-grid). Model: Claude Opus 5.5.

## Symptom

`drive="inverter"` at 100 kHz, 13 000 rpm (L12): the log stops after
`SB: 1320 steps/period requested above the 144-node slip ring — RAISING the
ring to 1320 nodes/period (9240 on the full circle)`; two runs were stopped
after 2 h with no result. The earlier note ("mesh build stalled") was wrong.

## Diagnosis

`faulthandler` stack dumps every 4 min (6 dumps, the last 3 after the ring
was raised) put the main thread in the **frame loop**, not in a mesher:
`p2_drive.ve_newton → p2_nonlinear.solve_ff → pardiso` (most dumps) and
`p2_projection.SlipProjection.build` (the per-frame slip weld). The gmsh
worker was idle. The run was progressing — only slowly.

Why it is slow: steps per period = 20 samples per carrier × f_sw / f_el
(48 kHz: 640, 100 kHz: 1 320), and the slip ring is raised to the step count
so the rotor moves one node per step. Doubling the steps therefore doubles the
frame count AND roughly doubles the band's dofs per frame, plus the per-frame
`SlipProjection.build` is a pure-Python signed union-find over all dofs.
Cost ≈ (steps/period)² → a 48 kHz run (≈ 80–90 min here) becomes ≈ 5–7 h at
100 kHz under the same load.

## Options (not done)

1. Fewer samples per carrier at 100 kHz (10 instead of 20 → 660 steps, the
   48 kHz cost); check the ripple loss against the 20-sample run once.
2. Cache `SlipProjection.build(m)` per ring shift (the shift sequence repeats
   every period) or vectorise the union-find.
3. Decouple the slip-ring node count from the time step (interpolating slip
   at a fixed ring), so the band does not grow with f_sw.

Until then the card's 100 kHz motor PWM loss stays the labelled estimate:
48 kHz FEM × (48/100)^1.5, range (48/100)^2 … (48/100)^1.
