# Propeller S1 runtime integration contract — 2026-10-07

This is a source audit and implementation brief for the offline propeller-load S1 search. It does not report a solved operating point. The current private bridge deliberately refuses before importing or calling the coupled route because it cannot yet establish the full runtime identity. The job store and point/search modules are coordinators and evidence mappers; they are not a production endpoint or qualification path.

## Safe request and identity sequence

1. Admit only a verified signed-in account for a customer-scoped job. `auth.resolve_user_detail` / `auth.caller_identity` establish the account; `workspace.workspace_for_request` binds the authenticated request to its workspace when `WORKSPACES_ROOT` is configured. `caller_identity` alone also returns admin and anonymous identities, so it is not a signed-in admission check. If customer isolation is a requirement and workspace resolution lands on the process workspace, refuse instead of running against the owner's machine. Never log or persist the bearer token.

2. Resolve selection with `routes.account.get_last_motor` and require an exact request selection match: `{ref_id, die, config, duty}`. That route validates the signed-in account, calls `family._require_die_access`, loads the named configuration, verifies the duty exists, and checks any catalog `ref_id` resolves to the same die. Its same-die rule intentionally permits an L12 passport reference for a selected L20 configuration. The reference supplies comparison/provenance only: it must not choose the active config, duty, geometry, winding, materials, or operating point. Resolve the actual selected build from `family._cfg_file(die, config)` and its die file; `family.payload(die, config, duty)` documents the merged geometry, winding, materials, parts, and saved duty representation, but is a read-only apply payload, not proof those values are what the unchanged solver currently reads.

3. Reconcile selection to the private workspace actually used by the child. `family._ctx_file` is workspace-scoped, while `family.context` reads that active workspace context and access-filters it. `routes.coupled._duty_summary` reads `duty_results.active_context()` and `family.duty_entry`, so the active `{die, config, duty}` must be seeded into the isolated workspace and independently checked against the signed-in selection before route import. Do not call the admin-only family activation writer to switch a customer's context. `family._read_ctx` alone is not an authorization check.

4. Freeze and resolve actual physics inputs before allocating expensive work. The current bridge already expects a private snapshot and hash manifest, and calls `passport_v1.snapshot.machine_snapshot` to compare `geometry.resolved`, winding/turns/connection, resolved material assignment records/cards, mesh settings, pack settings, reference tuple, duty, and manifest-derived source hashes. Keep the active L20 configuration and duty as the authority even when `ref_id` names a same-die L12 passport. Resolve effective parts and owner override/reference/excluded states from the selected configuration/workspace exactly as the build loader does; do not replace them with a passport's older part-state defaults. The bridge presently still marks these as unresolved: active authenticated family context, actual runtime drive settings, cooling settings/limit provenance, and solver/runtime provenance.

5. Bind each RPM trial to one exact request and one exact response. `coupled_propeller_s1_point.evaluate_propeller_rpm` computes prop load with `propeller._build` / `propeller.operating_point` from the pinned propeller source, requires identity/context/source matches, freezes each body, and maps the returned coupled response. Its motor shaft torque uses `transient.summary.P_shaft_net_W / omega`; `P_shaft_W` is shaft eddy loss and is not delivered output. The point adapter requires explicit solver and physical-gate evidence and preserves decoded raw responses on refusals. The wrapper must stamp the actual private-workspace/build identity after resolving it, not echo caller-supplied identity as if it were a readback.

## Inputs and hard integration gaps

- **Selected build and duty.** `family.payload` merges die geometry with configuration overrides and adds the chosen duty and duty materials, but the solver reads the effective `motor_config.yaml` through `config.get_config`, workspace bindings, and live simulation state. The private child must verify that its resolved workspace machine matches the selected family payload before the first trial. Duty current/RPM/angle and saved summary are in the selected config's duty; seeds/defaults must not come from a different duty or an L12 reference.
- **RPM binding.** `routes.simulation._effective_rpm` resolves the request RPM or saved `simulation.rpm`. More importantly, `routes.coupled._preflight` rejects a body RPM that differs from the configured RPM because the thermal loss-map half reads the configuration speed. A body-only RPM sweep through unchanged `coupled._run` therefore cannot traverse the domain. The next implementation must either provide an audited, isolated per-trial RPM rebind so both EM and thermal loss-map resolution see the same requested RPM, then verify that readback while preserving the frozen *build* identity, or remain blocked. It must never change the live/shared configuration. There is no established route flag in this checkout that makes an arbitrary RPM override thermally consistent.
- **Drive/electrical limits.** `_coupled_drive`, `_inverter_settings`, `_controller_settings`, `_drive_v_dc`, `_drive_carrier`, and `inverter.drive_source.controller_block_for` resolve drive settings with request/config/duty fallbacks and named sources. The exact resolved block and its source chain must be part of the identity. `transient.summary` reports the solved physical result, but coupled's ordinary response does not by itself prove an electrical-within-limit verdict against every active battery/controller/drive constraint. Derive explicit observations only from resolved declared limits and the solver's matching response; a missing limit or missing comparator is `unknown`, never an assumed pass. For a current-drive candidate, requested current is a fixed trial input; do not treat that alone as proof of voltage, battery, or controller feasibility.
- **Cooling/thermal limits.** `/api/propellers/cooling-options` (`routes.propellers.get_cooling_options`) is the allowlist/default authority; the prop's `selectable` and measured/tested RPM domain and `propeller.operating_point(...).extrapolated`/`power_estimated` fields must be retained. The same selected prop, position, ambient/altitude, and candidate RPM must feed both `propeller_point` and `thermal_settings` (`airSpeedSource`, `propellerId`, position/context, computed `airSpeed`). `thermal_settings.propeller_cooling_context_issue` is a request guard, not runtime identity evidence. Thermal response components provide observed temperatures; coupled `time_to_limit`/limits and `thermal` map can provide the named threshold and source when present. The point adapter's gate envelope must contain sourced numeric observations for coil and hottest magnet, with the response temperatures equal to those observations. No map, no limit, no source, or mismatched observations means `unknown`.
- **Mechanical gate.** `_mechanical_step` is opt-in, reads per-user mechanical panel settings, and catches errors into a response; the resulting coupling block can include `ok`, `sf_min`, and primary case data. `sf_min` alone is not an acceptance verdict, and `ok` only means the route produced a result. Request the actual mechanical solve with the candidate's RPM, delivered torque and coupled temperatures, then require an explicit configured acceptance threshold and comparable result evidence. If that threshold/source or required mechanical output is absent, the physical gate remains unknown. Do not infer a universal safety factor or speed limit.
- **Solver gates.** The actual coupled response is `{ok, coupling, transient, thermal, ...}`. `coupling.converged` covers EM/thermal iteration only; it is not nonlinear convergence or qualification. The point adapter reads `nonlinear_converged` from `transient`/`transient.summary`, and eddy, demag, steady-state gates across transient/coupling layers with explicit false vetoing true. Missing/non-boolean gates remain unknown. The existing `coupled._preflight` specifically refuses this coupled route when the request has `eddy=false` or `rotor_eddy=false`; that route contract is not a universal claim that every Simulation run must enable both. Preserve the selected Simulation/request controls exactly and never silently turn them on. If this route's required physics coverage is absent or contradicted in the solver response, refuse qualification. For an accepted coupled trial require `solve_to="steady"`, `coupling.converged is true`, and raw evidence for nonlinear, eddy-settled, demag-settled, and steady-state gates. Keep the complete per-trial raw response and provenance.
- **S1 meaning.** `coupled_continuous_rating.rate` estimates current at one fixed reference RPM/current from a thermal/loss model and does not search propeller load torque over RPM. It is not a propeller-load-curve maximum and must not be presented as one. The bounded search's `candidate` is a sampled/locally refined candidate, not a certified global maximum; domain-end feasible remains domain-limited, and unresolved/unknown regions above the candidate prevent a global claim. Current propeller sources with estimated power or RPM extrapolation cannot be marked fully verified.

## Dispatch, cancellation, and persistence

Expose the coordinator only behind an authenticated API/job route. Revalidate die visibility and selection in that route; copy the authorized workspace and required read-only catalog/material/propeller inputs into a unique private job root; verify source/code hashes in the child; never point the child at production/default/live mutable roots. Use `jobs.queued`/`jobs.run_job` with a fresh run ID and normal owner authorization. Poll `jobs.check_cancelled(run_id)` before every canonical solve and between RPM/current evaluations. The current bridge's `_dispatch_and_envelope` uses blocking `subprocess.run(timeout=...)`, so queue cancellation cannot promptly stop its child and timeout/refusal storage currently keeps only a small refusal marker, not the last completed raw point. Replace this with an owned child-process handle polled by the queue job; on cancel/timeout terminate only that job's process group/tree, wait for it, and persist cancelled/timeout state plus completed callback replies. Add child-to-parent checkpoints between canonical runs; do not claim an in-progress FEM response is recoverable after forced termination unless the solver exposes a verified checkpoint. Cancellation and canonical-call-budget exhaustion must stop before the next callback and persist separately from physical infeasibility. The existing `PropellerS1Job` already provides one-shot IDs, reservation, global callback budget, result identity digests, and `publication_qualified=false`/`global_max_certified=false`, but it is not wired to the API jobs queue or account/workspace admission.

The canonical callback cannot use `record:false` for multi-pass steady coupling: `routes.coupled._run` explicitly refuses `max_iter > 1` under record suppression. The private child therefore needs an isolated workspace with record enabled, a fresh coupled run per trial, and no history reuse (`fresh=true`); private persistence must stay separate from the customer's duty results until a later explicitly reviewed publication flow. Preserve each raw response/refusal in the private job record. Do not write a candidate back to Configure, family duty records, or catalog during the search.

## Later Configure consumer

Configure should consume only a completed per-user result whose build, duty, propeller source, drive, cooling boundary, and result digest still match its currently resolved inputs. Display the searched domain, resolution, tested propeller RPM range, each evaluation's torque/current/thermal/electrical/mechanical evidence, and unresolved/estimated/extrapolated points. Results are advisory until a separate qualification/publication gate exists. The current finite search deliberately leaves `global_max_certified=false` and `publication_qualified=false`; sampled refinement is not a mathematical proof of a global maximum. A later certificate must describe the actual bounded-search guarantees and gate evidence without claiming more. Do not overwrite the saved duty's fixed RPM/current/drive or treat its L12 reference ID as the selected L20 build. Re-run or invalidate the cached candidate whenever any identity block changes; never reuse another build's job result.

## Remaining blockers before a first real candidate

1. Implement verified account + workspace + selection admission for the new job route and cross-check `last_motor`, selected config/duty, per-workspace family context, and isolated child context.
2. Resolve exact active build, part states/material overrides, mesh, drive/controller/pack, cooling settings and limits, prop source, and source/code revision; compare these against the frozen identity. The current bridge explicitly refuses this missing evidence.
3. Resolve the RPM/preflight mismatch with a narrowly audited private-workspace seam so the unchanged EM and thermal loss map both run at each requested RPM. The isolated `coupled_propeller_s1_trial_context.materialize_trial_context` helper now supplies a pure copy-and-readback primitive for an already-private manifest-verified workspace; it has no auth, API, or solver integration and is not proof that either solver consumes the copied RPM until the child verifies it.
4. Supply physical electrical and mechanical limit observations from declared resolved limits; current coupled output does not provide a complete explicit verdict for these gates.
5. Wire cancellation/progress into the existing queue, retain raw responses and refusals, and keep results private/unqualified. Test all of the above with fakes before any solver launch; then separately authorize and journal a bounded real compute run.
