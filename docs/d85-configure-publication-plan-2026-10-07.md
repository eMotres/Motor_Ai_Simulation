## Existing Configure read path

The release UI obtains reference cards through `fetchCatalogReferencesAnswer()` in `web/src/lib/referencePassports.ts`, preferring `GET /api/catalog/references`. The route in `src/motor_ai_sim/routes/catalog.py:get_references()` serves only catalog entries with the legacy analytical shape (`passport.passport`); it filters private cards and die grants for the caller, computes `has_machine`, and asks `passport_store.attach()` to append computed `pwm_variants`. The v1 passport store is read-only and supplies drive variants; it does not create or replace the legacy base analytical passport.

Configure converts each returned entry only when `passport`, `geo`, and `fit` are present. `ConfiguratorPanel.tsx` first matches a loaded build by section geometry (slot count, pole count, stator outer radius within 0.5 mm, magnet height within 0.3 mm), then scales from its passport build values. A loaded saved selection is pinned by catalog reference id and die. `lastMotor.ts:rememberLoadedMotor()` chooses the exact card configuration when present, but can fall back to the first card on the same die; D85 publication therefore must provide an exact L13 card and must test that exact choice, rather than rely on that fallback.

The normal account flow is `PUT /api/me/last_motor` in `routes/account.py`, which validates the selected family die/config/duty and resolves the supplied reference through the caller-visible catalog references, requiring the card's die to match. Configure's read-only `GET /api/catalog/{motor_id}/configure_context` additionally checks card visibility and grants, then resolves that card's family config and presets. A customer check must use a normal permitted account with the D85 die grant, confirm the exact reference appears in `/api/catalog/references`, select/load L13, and verify its saved `ref_id`, Configure match, pack/preset context, and PWM variants. An admin-only successful lookup is not sufficient evidence of customer visibility.

The existing `POST /api/catalog/{motor_id}/passport` is not a candidate-import endpoint: it requires a catalog card with a preset, runs `passport.generate_passport()` and its own characterization work, then attaches that newly generated record to the card. `POST /api/presets` saves a preset and creates a catalog card, but does not attach a passport. `passport_store.attach()` only decorates existing passport cards with PWM variants. There is no current route that safely imports the finished isolated candidate without regenerating it. Do not hand-edit the shared Drive catalog or repurpose the generation route in a way that launches another solve.

1. **Close the isolated run from its final immutable evidence.** Require an explicit terminal checkpoint, no started-only callbacks, expected generator/replay consumption counts, and the exact frozen solver source, snapshot, geometry/material signatures, assignments, temperatures, effective shaft state, request digests, and raw reply hashes. Require every ordinary point's original affirmative gates: `steady_state`, `qualified`, `nonlinear_converged`, `eddy_settled`, and `demag_settled` when requested. Retain the owner point's false raw gates verbatim and verify its exact owner record against the archived raw reply and sole waived residual. If any other owner-point check fails or any ordinary sample is missing/unknown, do not make a candidate available to customers.

2. **Build a staged legacy-card candidate, not a live catalog write.** Validate the actual candidate shape against the unchanged `passport.generate_passport()` schema consumed by Configure: the outer `passport` object must include its nested analytical `passport` plus the matching `fit`, `geo`, pole and slot fields. The displayed geometry and winding/material/build inputs must describe L13, not the older `cat_ciano28_85` base card or `ciano28_85_13` preset. Attach a machine-readable, exact-hash `reference_preparation_disposition` for point 3 outside raw solver status. Keep `publication_allowed=false` until the remaining checks and the explicit parent publication review pass.

3. **Use a reviewed import/write seam.** Before any shared catalog mutation, add or identify a narrowly scoped admin/owner-authorized import path that accepts only the staged candidate and its complete provenance manifest, checks exact D85/L13 identity and existing family/preset ownership, rejects altered/missing hashes and all non-target exceptions, then atomically attaches the legacy card to the exact `CIANO28 85 20SW1200 L13` catalog entry. The current release has no such import operation. A server-side adapter must persist the point-3 raw failure and owner disposition in an inspectable provenance location and must not map them to global `qualified=true`, `steady_state=true`, or S1 fields. Do not publish by writing `/srv/motres/shared` or a catalog file by hand.

4. **Prove the existing consumer contract before enabling a public card.** In an isolated catalog/family fixture, run the established passport-store/reference/catalog tests and add a D85-specific exact-L13 fixture test. Verify the public/allowed reference contains the legacy wrapper shape, `card={die,config,date}` resolves to D85/L13, `has_machine=true`, v1 drive variants attach only from the matching L13 store record, and no same-die fallback selects the older D85 geometry. Then verify `PUT /api/me/last_motor` / Configure restoration for a permitted ordinary user and a denied/ungranted user. Confirm Configure shows a normal reference and its provenance annotation does not describe it as an S1 or continuous propeller rating.

5. **Keep rating publication as a different gate.** The Configure reference may describe its analytical baseline and its measurement/exception provenance, but no record from this fixed-current harness may be labelled a maximum propeller S1 RPM. The eventual propeller S1 result needs the actual assigned propeller, torque-matched solved motor point and speed, same-point voltage/current/thermal/mechanical evidence, settled flags and qualified search boundary, plus its own input/source hashes. It must remain unknown/unpublished wherever the search has unresolved samples above the reported boundary.
