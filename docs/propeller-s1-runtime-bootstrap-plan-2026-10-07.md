# Propeller S1 runtime identity bootstrap plan — 2026-10-07

This note records the missing bridge between an authenticated immutable snapshot and the runtime identity consumed by `PrivateCoupledBridge`, then the bounded offline implementation checkpoint. A successful bootstrap establishes build identity only; it does not qualify a motor point, certify an RPM maximum, or permit publication.

## Finding

The snapshot path already produces a useful trusted starting record. `coupled_propeller_s1_snapshot.create_private_snapshot()` authenticates the bearer through the configured private-auth provider, reads the caller's `account.get_last_motor()` selection, requires the active `family._read_ctx()` tuple to match, checks die/config access, and copies a hash-manifested workspace/build/source set. It records `expected_selection`, `owner_sha256`, `snapshot_inputs`, and a validated `body_template`. The context key is derived from the verified account plus selected die/config/reference in `_bind_authenticated_propeller_context()`; the raw account identifier is not needed in the public job record.

The next step is not wired. `PrivateSnapshot.make_private_job(identity=...)` requires a complete identity from its caller and explicitly does not create or bless identity evidence. `PrivateCoupledBridge._validate_job()` requires that identity before a bridge instance can be created. Its worker later calls `_resolve_runtime_identity(expected, ...)`, which independently rebuilds the passport snapshot and authenticated runtime context, calls `build_runtime_identity_v2()`, and compares that observation against the supplied identity before invoking the canonical coupled run. Consequently the normal trial path is intentionally compare-only: it cannot be used as the first source of `expected` without an additional bootstrap operation.

This is a control-flow gap, not a reason to accept client-supplied identity. Do not seed `PrivateJob.identity` from request JSON, from an unchecked snapshot field, or by copying an identity sent by the browser. Do not weaken the existing per-trial identity comparison.

## Minimal two-stage handoff

1. **Admit the ordinary queued job before any child process.** Use the existing `jobs.queued(...)` route wrapper and wait until its background worker holds the normal queue slot. Snapshot/bootstrap work runs only inside that worker, where `jobs.current_run_id()` is available and cancellation can be checked. No child process starts in the HTTP submission handler or before queue admission. The worker then uses normal bearer verification and workspace selection and calls `create_private_snapshot()` with a server-constructed closed solver-body template and the caller's assigned propeller. It accepts only bounded search parameters from the client. Owner, family selection, saved drive/cooling controls, propeller assignment, context key, and solver identity are resolved server-side. The snapshot and all manifest/code/source hashes are kept in a private job root. The exact selected `die/config/duty/ref_id` tuple is retained as the snapshot's comparison value, not as authority submitted by the client.

2. **Run a dedicated solver-free child preflight.** Launch one fresh child using the already-reviewed process supervisor and the same private job/source manifest. Give it the genuine bearer through the existing transient stdin channel, the frozen snapshot paths/hashes, the server-issued selection/owner-hash comparison values, and the one canonical full request body used as the bootstrap operating-point seed. Classify `configured_process_auth_source()` in the trusted supervisor before constructing a child environment with job-local `MOTOR_AI_SIM_CONFIG`; never mutate the server process environment. Carry the trusted auth root and file/environment source kind in the child environment only. In environment mode the child inherits the already-configured secret only for its own process, not in argv, stdin, files, manifests, result, exception text, or logs. File mode omits `AUTH_SECRET`. The existing provider then rereads current users and sessions and verifies the actual token; this is not a new principal or an auth bypass.

3. **Resolve actual state inside the child.** Reuse the strict stdlib manifest and path admission, enter `use_private_auth()` before lazy auth/account/family imports, and bind a job-local `Workspace` plus the caller proven by the bearer. Read live account selection again and compare it to the snapshot tuple; check `family._read_ctx()` and exact selected die/config/duty files against the manifest; re-read the runtime motor config and `family.payload()` geometry/winding/material/duty; use the saved passport, material card, mesh, pack, parts, drive and cooling source resolvers. Resolve the assigned propeller/position/ambient from the same snapshot and recompute its candidate point at the seed RPM. Produce the actual runtime context through the same readback used by `_resolve_runtime_identity.finalize`, including selected payload, drive/cooling/mechanical inputs, battery readback, source hashes and release code hashes. This phase must not call `_invoke_canonical_run`, `_run`, `routes.coupled.run`, FEM, or any result-producing solver callback.

4. **Build identity from observed values, not a caller echo.** In the child, call the existing `build_runtime_identity_v2()` on the re-read `machine_snapshot`, authenticated selection, resolved runtime context and canonical body. For PWM, validate the full point-specific drive readback and request with `bind_pwm_trial()`, then produce the invariant PWM projection with `invariant_pwm_identity()`; reject inconsistent fixed-bus, modulation, connection/grouping, parallel-count, or terminal-topology readbacks. Return a typed `identity_preflight` record containing the canonical actual identity, its canonical digest, and hashes binding the job snapshot manifest, body template, seed request, propeller source and code/source manifest. Include an explicit `solver_calls: 0`. Do not return the bearer, raw account email, users/session data, secret, or raw context key.

5. **Verify and freeze before constructing the search coordinator.** Queue admission has already happened in step 1. The supervisor accepts only the expected preflight schema/state; recomputes the canonical identity digest; requires exact job ID, snapshot/manifest digest, body-template digest, seed request digest, selection comparison, propeller source/implementation hashes and release-code manifest; rejects extra auth fields; and persists the identity plus the preflight envelope before constructing `PrivateJob`. For PWM, the persisted job identity is the verified invariant projection, while its full candidate readback remains per-trial provenance. The `PropellerS1Job` stores the same frozen identity digest and search-domain policy. A preflight refusal creates no runnable search coordinator. The normal child for every RPM/current trial still reauthenticates and independently rebuilds/comparisons the full actual identity before the solver callback; a user/session/build change between preflight and a trial therefore fails closed.

The bootstrap preflight is the first place an identity can be trusted, but it must not become a long-lived permission token. The child proves what the live authenticated build resolved at that instant; every actual trial rechecks current session and build state. Its identity output contains only opaque owner/context digests and engineering inputs. Keep the auth source paths outside the engineering manifest, and persist only the authentication-source kind and redacted verification status.

## Smallest source and test changes for a future implementation

- Add a preflight operation to the private worker protocol with a schema/state distinct from `--worker` trial execution. Keep the existing stdlib admission and private-auth provider checks. Make the operation return only after runtime resolution, without importing or calling the coupled execution function. Do not add an HTTP endpoint until this offline seam and its tests pass.
- Refactor the readback finalizer into a shared resolver that can either (a) compare the freshly observed identity against a frozen identity for normal trials or (b) return that observed identity to the supervisor during the one-time preflight. In preflight mode, authenticate first and derive the owner/context internally; pass only the snapshot-created owner hash and selection tuple as expected values, not an identity object. The first mode must preserve every existing comparison and refusal in `_resolve_runtime_identity()`.
- Extend the supervisor's result validator to accept the preflight record only for a freshly reserved job and exact snapshot/body/source/code digests. Use an exclusive bootstrap-result file or equivalent protected private handoff; do not use a mutable result path which can be overwritten by caller input. Scrub the bearer from any persisted failure data and never include auth values in errors.
- Build the solver body from saved Simulation/drive/cooling settings and a strict route whitelist. A browser-supplied body is not a trustworthy identity seed. Search RPM/current bounds are job options and computational domain metadata, not equipment limits. Preserve `expected_selection.ref_id` as the same-die passport reference and `selection.config` as the actual selected build; do not substitute the reference configuration.
- Add no-FEM tests for: forged client identity ignored; correct authenticated snapshot/body readback creates identity; another account, revoked/missing session, changed `last_motor`, changed active family tuple, or changed source manifest refuses; missing/invalid resolved drive/pack/cooling/material/winding evidence refuses; PWM uses the full resolved identity then its invariant projection; malformed or tampered preflight output, request/hash mismatch, or duplicate bootstrap cannot create a job; assertion that the bootstrap callback count and canonical solver call count are zero; and the following real trial still reauthenticates and compares. Existing normal auth and Configuration workflows must remain unchanged.

Before public wiring, retain the API queue's per-user ownership, normal visibility checks, explicit cancellation, and private child process-tree cleanup. The current S1 coordinator and bridge are not registered as an authenticated public job route or Configure result consumer. Parent-process `os.environ` changes are forbidden: module-level config paths are fixed at import time, so the job-local config belongs only in the child environment. The production auth source has been observed as environment-backed; do not describe the child as sandboxed or least-privileged, because it runs under the same OS account and receives the configured key in environment mode.

## Qualification boundary

An identity bootstrap cannot establish torque equilibrium, voltage feasibility, converged thermal limits, contact/mechanical safety, demagnetization stability, or a highest feasible RPM. The existing point/search records must continue to distinguish unknown, verified-feasible, and verified-infeasible samples; `publication_qualified` and `global_max_certified` stay false. Actual acceptance still requires same-point torque/load evidence, named thermal/electrical/mechanical gates, measured propeller-domain coverage and no unresolved region above the reported candidate. No new FEM or browser-visible result is authorized by this audit.

## Offline implementation checkpoint — 2026-10-07

The isolated release now has `coupled_propeller_s1_bootstrap.bootstrap_runtime_identity()`, which refuses unless called inside an already admitted `jobs.queued(...)` worker (`jobs.current_run_id()` must be present). It rechecks snapshot and release manifests, reserves a unique identity attempt, classifies the trusted auth source before building the child environment, checks cancellation before spawn and through the process supervisor, and accepts only a child-observed runtime-v2 identity whose canonical digest, selection, body, source, implementation and code-manifest bindings match. The child operation is explicitly `--identity-preflight`; it enters the existing no-copy auth provider, runs the same source/runtime readback and unchanged coupled-route `_preflight`, recomputes the propeller point, and returns before any canonical EM/thermal/mechanical solve callback. The identity result is saved create-only without bearer or raw account/context data.

The shared resolver now has a distinct `expected=None` observation path; ordinary solve calls still use the original strict expected-identity comparison path. The process attempt guard accepts only `propeller-s1-private-job-v2`, matching the snapshot writer and bridge; the legacy v1 marker is explicitly refused. These changes do not add or wire a public route, UI, `PrivateJob` factory, search submission endpoint, or Configure result consumer. The next integration step must call bootstrap only from the scheduled worker after ordinary queue admission, then pass the returned identity to private-job construction. No result is qualified by this checkpoint.

The first focused offline verification run passed 103 tests with 2 existing skips across the bootstrap, process-control, and private-bridge suites. It used fake process callbacks and fixture-only auth context; no live API, FEM, Linux worker process, deployment or physical result was exercised. This is an implementation test result, not proof that actual production runtime identity admission has been launched.

## Bounded review follow-up — 2026-10-07

Review found that Python equality treated `False` and `0.0` as a successful process return code, and that strict checkpoint-path resolution could raise before sanitized refusal evidence was written. The supervisor now accepts only a type-exact integer zero for both the process outcome and checkpoint, rejects missing, linked, or non-exact checkpoint paths, and writes a create-only refusal record with a reason code and exception class only. Checkpoint filenames and exception text are not persisted.

The composed expected-identity-free test exposed an unset auth-event directory: bootstrap supplied its attempt directory, but the shared resolver only resolved it for normal trial mode. The resolver now resolves and bounds the bootstrap attempt directory under the admitted job's `attempts` tree before directing auth audit events there. A fixture-only integration regression exercises the real `_resolve_runtime_identity(None, ...)`, official temporary auth/session verification, actual selected geometry/winding/material/selection readbacks, and the unchanged `routes.coupled._preflight`; it asserts the canonical solver callback is not reached. A changed saved selection is refused before that callback.

The final focused run passed **110 tests with 2 skips** across `test_propeller_s1_bootstrap.py`, `test_propeller_s1_private_bridge.py`, and `test_propeller_s1_process.py` (49.53 seconds). The first run of the new composed tests exposed the missing bootstrap attempt-directory binding and incomplete fixture cycle settings; both were corrected before the final run. Tests used temporary fixture stores and callbacks only. No process child, API, network, FEM, deployment, or physical result was exercised; actual bootstrap has not been launched.
