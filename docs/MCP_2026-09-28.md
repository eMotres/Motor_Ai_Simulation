# eMotres MCP server: Stage 1 (read-only), 2026-09-28

External AI agents (Claude Desktop, Claude Code, later ChatGPT) reach the
eMotres catalog and saved simulation results at **`https://emotres.com/mcp`**
through the Model Context Protocol. Stage 1 is read-only. It runs no solver
and exports no geometry.

## Architecture

- Uses the official MCP Python SDK (`mcp==2.2.0`, `MCPServer`) with the
  **streamable HTTP** transport in **stateless + JSON-response** mode. Each POST
  is one self-contained JSON-RPC exchange, so there are no SSE streams, no
  session affinity and no special nginx buffering.
- **Where it runs:** inside the FastAPI API process, so it uses the same
  stores and the same permission code as the web. It is not a separate
  service. `motor_ai_sim.mcp_app.McpGate` is added as the **outermost** ASGI
  middleware and takes `/mcp` before the tier gate, the workspace resolver and
  CORS see it. Those layers understand session tokens, and an agent key is not
  a session token. We chose this over a separate ASGI app because a second
  process would need its own copy of the catalog/workspace/grant logic, and two
  copies of an access rule drift apart. nginx adds only `location = /mcp`
  (`deploy/nginx.conf`). The API container and compose file are unchanged.
- McpGate does this for every request:
  1. **Auth:** checks `Authorization: Bearer emk_<id>_<secret>`. On failure it
     returns 401 with `WWW-Authenticate` and a `reason` (`no_token`,
     `malformed`, `unknown_key`, `revoked` or `disabled`).
  2. **Scope:** on `tools/call`, the tool's scope must be on the key.
     Otherwise it returns 403 (JSON-RPC error -32001).
  3. **Quota:** on `tools/call` only, it counts per key per minute and per UTC
     day. Over the limit it returns **429 with `Retry-After`**.
  4. **Audit:** it writes one JSONL line per tool call (and per auth
     failure): time, user, key id, tool, args summary (≤300 chars), status.
     The file is `config/mcp_audit.jsonl`, next to `users.json`.
- The tools run as the key's owner. `auth.use_agent_user` makes every
  in-process check answer exactly as that owner's own web session would:
  `motor_access.catalog_access`, the per-user die grants,
  `routes.family.tree`, and the workspace layers (own / published / shared).
  `list_machines` calls the **same `family.tree()`** the Motors tab calls.
- Data leaves through a **whitelist**. `mcp_tools.GEOMETRY_DENYLIST` is also
  checked on every answer before it is returned: no stator/rotor dimensions,
  no winding geometry, no thumbnails/SVG, no build signatures and no B-H
  curves. A machine is described only by outer diameter, active (stack)
  length, mass, slot/pole count, material names, ratings, losses and
  temperatures.

Files: `src/motor_ai_sim/agent_keys.py` (keys, quota, audit),
`src/motor_ai_sim/mcp_tools.py` (tool logic),
`src/motor_ai_sim/mcp_app.py` (SDK server + gate),
`src/motor_ai_sim/routes/agent_keys.py` (web API),
`web/src/components/auth/AgentKeysDialog.tsx` (UI),
`tests/test_mcp_stage1.py`.

## How an owner creates a key

1. Sign in on emotres.com, click the avatar, then **Access for agents**.
2. Enter a name (for example "Claude Desktop"), tick the scopes
   (`catalog:read`, `machines:read`) and click **Create key**.
3. Copy the `emk_…` token. It is shown **once**. Only its SHA-256 is stored
   (`config/agent_keys.json`).
4. The same dialog lists your keys with their scopes, creation date and last
   use (updated at most once a minute). **Revoke** takes effect on the next
   call. When an account is disabled, all its keys stop working.

API: `GET/POST /api/agent_keys`, `DELETE /api/agent_keys/{id}`, and
`GET /api/agent_keys/audit` (your own last calls). Each account can have at
most 10 active keys.

## Connecting a client

**Claude Code**

```bash
claude mcp add --transport http emotres https://emotres.com/mcp \
  --header "Authorization: Bearer emk_XXXXXXXX_YYYYYYYY"
```

**Claude Desktop** (`claude_desktop_config.json`). The Desktop connector UI
only does OAuth for remote servers, so until Stage 2 use the `mcp-remote`
bridge (it needs Node.js):

```json
{
  "mcpServers": {
    "emotres": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://emotres.com/mcp",
               "--header", "Authorization:${EMOTRES_KEY}"],
      "env": { "EMOTRES_KEY": "Bearer emk_XXXXXXXX_YYYYYYYY" }
    }
  }
}
```

**ChatGPT connectors / claude.ai custom connectors.** These accept only OAuth
(or no auth) for remote MCP servers, so they need **Stage 2 (OAuth 2.1)**. The
URL will stay the same.

**Raw test**

```bash
curl -s https://emotres.com/mcp -H "Authorization: Bearer emk_…" \
  -H "Content-Type: application/json" -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

## Tools (all read-only, `readOnlyHint: true`)

| tool | scope | what it returns |
|---|---|---|
| `list_catalog(kind, query?)` | catalog:read | Entries of kind `magnets`, `steels`, `wires`, `bearings`, `devices` or `dies`, with key specs in unit-named fields plus a `provenance` block (source, datasheet, curves present). Dies are only those this account can see. |
| `get_catalog_entry(kind, id)` | catalog:read | One entry. |
| `list_machines()` | machines:read | Own, published and granted machines: die, config, ownership, OD/active length/mass, slots/poles, materials, DC-bus voltages, and per duty `torque_nm`, `power_kw`, `speed_rpm`, `efficiency_pct`, `line_voltage_peak_v`, `mass_kg`. |
| `get_machine_performance(die, config, duty)` | machines:read | Operating point, loss split (core/copper/solid/mechanical W), temperatures (coil/magnet/bearing °C, cooling), continuous rating, time to limit, KV, ripple, duty cycle. A machine that is not visible gets the same "not found" as one that does not exist. |
| `check_fit(torque_nm, speed_rpm, voltage_v?, max_diameter_mm?, max_length_mm?, max_mass_kg?, cooling?, limit?)` | machines:read | Duties that deliver at least `torque_nm` at `speed_rpm` or faster, with peak line voltage ≤ `voltage_v` (DC bus) and OD, active length and mass within the limits. Results come with margins in %. Ranking: fewest unverified checks, then lightest, then most efficient. Rejected duties are listed with reasons. |

Resource: `emotres://guide`, a short usage guide in Markdown.

## Configuration (env)

| var | default | meaning |
|---|---|---|
| `MCP_RATE_PER_MIN` | 30 | tool calls per key per minute |
| `MCP_RATE_PER_DAY` | 2000 | tool calls per key per UTC day |
| `MCP_KEYS_DIR` | the `users.json` directory | where `agent_keys.json` and `mcp_audit.jsonl` live |

Quotas are counted in process memory, which fits the single API process on the
server. A restart resets the counters. Stage 3 moves them to the job-queue
store.

## Stage plan

- **Stage 2: OAuth 2.1, following the MCP authorization spec.** The API
  becomes a protected resource with `/.well-known/oauth-protected-resource`,
  and the existing self-hosted login is the authorization server
  (`/.well-known/oauth-authorization-server`, authorization-code + PKCE,
  dynamic client registration for ChatGPT and claude.ai connectors). The
  consent screen shows the scopes. Nothing breaks for keys because every
  credential already resolves to one `agent_keys.Principal(email,
  credential_id, kind, scopes)`. `verify()` gains a second branch for
  `kind="oauth"` access tokens, which are stored hashed in a separate
  `oauth_grants.json` next to `agent_keys.json`. Scopes, quotas and audit are
  keyed on `credential_id` and apply unchanged. Keys stay for headless agents.
- **Stage 3: simulate through the queue.** New scope `simulate:run`, and
  tools `simulate_duty` / `get_job` that submit to the existing job queue
  (`jobs.py`, priority by tier) and poll. They never run inline and are
  never allowed on the owner's live API. Quota is counted in solver-minutes.
- **Stage 4: design and publication.** `design_request` / `request_quote`
  (scope `quote:write`, which creates a visitor request for the owner), plus
  publication of selected machines to an anonymous public tier (datasheet-level
  only), listed in the MCP registries.
