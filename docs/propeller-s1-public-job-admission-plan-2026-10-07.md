# Propeller S1 job admission contract — 2026-10-07

## Recommendation

Expose this as a new authenticated, queued `POST /api/coupled/propeller_s1` workflow. Keep `/api/coupled/continuous_rating` unchanged: it rates thermal conditions from an already-held electromagnetic run; it does not search propeller RPM or solve the motor/propeller torque equilibrium. The new route should snapshot the selected build and assigned propeller once, then use the existing `PropellerS1Job` → bounded RPM search → point adapter → private coupled bridge chain. It must report a finite-domain candidate, unresolved result, verified infeasible samples, cancellation, or budget exhaustion honestly; current search output always leaves `publication_qualified` and `global_max_certified` false.

The current bridge has no supported no-copy auth-store path, so the public job route should remain blocked until that boundary is addressed. `config.DEFAULT_CONFIG_PATH` is selected before module import; `users._USERS_FILE` and `users._SECRET_FILE` in `users.py`, and `sessions._SESSIONS_FILE` in `sessions.py`, are then fixed beside that config. The private child deliberately sets `MOTOR_AI_SIM_CONFIG` to its job-local `workspace/motor_config.yaml`, while `_bind_private_auth_storage` in `coupled_propeller_s1_private_bridge.py` requires the users, signing-secret, and session paths to resolve inside that workspace. `_REQUIRED_CONTEXT_FILES` explicitly includes `workspace/users.json` and `workspace/.auth_secret`; it does not itself list `.sessions.json`, but the binder still requires the session path to be job-local. Any admission builder that fills those required files from the installation auth store would create per-job copies; the bridge source shows no alternate store binding. The authoritative signing secret may instead come from the `AUTH_SECRET` environment override. The child launcher explicitly strips that variable, so a file-backed no-copy provider could reopen the trusted source file, but an env-backed secret cannot be read from the parent process by this child; silently falling back to a workspace `.auth_secret` would risk using a different key. For env-backed deployments, no-copy verification needs an explicitly reviewed parent-verification/capability path or auth service; do not pass the installation signing key in the job body, manifest, or result. Setting `workspace.use_caller()` is only a caller-context binding, not credential verification. The existing `auth.use_agent_user()` is an in-process MCP agent-key facility, not a cross-process user handoff; a plain caller dictionary passed over stdin would bypass the normal auth proof. Do not copy server auth stores into each job or fabricate a token/principal to get around these checks.

## Resolve the caller’s exact build before accepting work

At submission, use the actual request’s `Authorization` header and normal auth/workspace resolvers. `auth.resolve_user_detail` / `auth.caller_identity` establish the caller; `workspace.workspace_for_request` and the request middleware bind the account workspace and caller. Require a verified named user with the normal user-tier gate. Do not accept owner, die, config, duty, reference, propeller, or context identity as authority merely because the browser submitted them.

Read the current selection through `routes.account.get_last_motor`, which revalidates `ref_id`, die/config access, and duty. Read the active tuple through `routes.family._read_ctx`; require `die`, `config`, and `duty` to agree, and reject released or missing context. Resolve the selected family payload and files with the existing family access functions. The stored passport reference may name another configuration of the **same die**: `account._validate_last_motor` explicitly validates the reference card’s die while separately validating the requested configuration. Keep the selected configuration and duty as the actual build; do not rewrite L20 to the reference’s L12.

Resolve the propeller from the caller’s saved Thermal setting and validate it with `thermal_settings.propeller_cooling_context_issue` plus `routes.propellers.get_cooling_options(die, config)`. Require `propeller_air`, the exact assigned propeller ID, and a selectable measured-load source. Resolve its checked catalogue file and `propeller._build` source hash. Preserve the selected slipstream position and ambient temperature. A stale or unassigned propeller is a refusal, never a first-catalogue-item fallback.

Use the Simulation tab’s current operating point and the explicitly selected drive/build records. Do not substitute `motor_config.yaml`’s saved simulation current/RPM for the user’s active operating point. The `drive.current_setpoint_readback` currently documents `simulation.max_current` and `current_a` as setpoints, not capability limits; they may define a caller-approved computational search interval, but they must not become an equipment current rating. A sourced inverter/controller limit, if present, remains separately identified. If no physical limit evidence exists, keep the corresponding gate unknown.

## Snapshot and private-run boundary

Create a new per-job private root under a server-owned private jobs directory, disjoint from the release checkout, default config, live user workspace, shared catalog, and production paths. Use the source bridge’s strict path and symlink/junction checks. Construct the workspace from a whitelist rather than recursive copying. Freeze a manifest before queue execution and verify it before each point.

The minimal resolver inputs are the private job marker; the active user’s `workspace/motor_config.yaml`; `.family_context.json` and `.user_prefs.json` needed by the existing family and last-motor resolvers; the exact selected die/config files; the rated-duty and material/fallback files named by `snapshot_inputs`; the assigned propeller source; and the effective `cooling_options.yaml` layer. Include each exact runtime source file in the release code-hash manifest used by the bridge. The current bridge’s `_REQUIRED_CONTEXT_FILES`, `_REQUIRED_CODE_FILES`, and `snapshot_inputs` checks are the authoritative minimum; if a new read is introduced, add its path to that whitelist and hash it rather than relying on an untracked file.

Do not admit `.jobs.json`, sweep/optimizer journals, `.last_*` result stores, cached fields, stale resume state, or prior solve outputs as inputs. They are not build authority and would let the new solve consume or overwrite prior answer state. Preserve the selected build, materials, drive, ambient/cooling, parts, and all non-point physics settings unchanged. Only the per-trial RPM/current and source-defined PWM candidate fields may vary in each attempt workspace. The bridge’s trial-context helper materializes unique workspaces and changes only the approved effective simulation RPM/current; its readback then verifies the full base manifest and config semantics.

There is a narrow no-copy design for private auth that preserves unchanged route guards and needs no client Configure changes. Its opt-in provider is implemented offline but is not wired into the bridge. `private_auth_context.use_private_auth(auth_root, job_root=..., attempt_root=..., secret_source=...)` binds only trusted internal paths and a startup-classified `file` or `environment` source; it validates store paths and root separation without exposing or retaining secret contents/hashes. `use_file_backed_auth(...)` remains a strict compatibility wrapper that accepts only `file`. A read-only server check found the installed production secret source is `environment`; the new provider can verify against an inherited environment value, but that source is not yet bound to the bridge and no production readiness is implied. With the context active, `users.py` and `sessions.py` reread live user/session sources on every access, and the environment-mode secret is reread from `AUTH_SECRET` for each verification. Private HS256 verification requires a nonempty token SID and the exact live session record, with matching SID and normalized email, explicit `revoked: false`, and finite future expiry. Missing, malformed, mismatched, revoked, or expired sessions fail closed. The context suppresses session touch/renew and registry writes, refuses Google-token fallback rather than validating remotely or linking a user, and restricts rejection events to code/reason fields in an attempt-local sink. With no context, existing import-time auth paths and legacy-token/session behavior remain unchanged. Initial draft-only provider tests passed 10 cases but did not require an exact active-session record; the corrected session-binding suite passed 21 cases, and the added environment-source tests are separately verified below. No provider test wires auth into the bridge or enables a public route.

Integration still requires the private bridge to obtain the auth root and `secret_source` from server-startup/internal configuration (never request/job fields), bind this context around the pre/post identity checks and canonical `_run`, and remove the copied auth files from its job context requirements. Parent-side admission should call `private_auth_context.configured_process_auth_source()` before redirecting `MOTOR_AI_SIM_CONFIG`; it checks the already-imported `config.DEFAULT_CONFIG_PATH`, `users._USERS_FILE`, `users._SECRET_FILE`, and `sessions._SESSIONS_FILE` resolve to one link-free configured root, then returns only that root plus `file`/`environment` source kind. A missing configured config/store or mismatched path set refuses admission. The result is trusted bootstrap metadata, not a client/job field; never recompute it after the child config redirect. Keep `.user_prefs.json`, `.family_context.json`, selected family/config/duty files, and other engineering inputs in the job-local workspace snapshot; these are build state, not global credentials. The current `_bind_private_auth_storage` still demands job-local auth paths, so the implemented context alone does not enable no-copy child verification or a public route. The configured file-backed provider must reopen `users.json` and `.sessions.json` for each check so account disablement, role changes, and session revocation are not frozen at admission, and reread `.auth_secret` so rotation invalidates stale tokens. Private `sessions.read_events()` is scoped to the attempt-local redacted event sink, not the installation-wide auth log. Do not content-hash or copy live auth stores into the job manifest or result; record only non-secret verification provenance and the existing opaque owner/context digests.

The provider must remain explicitly read-only: the offline context disables sliding-token renewal, `sessions.touch`/`extend`, `_registry_role` auto-provisioning, Google-user linking, and writes to source auth stores. Route rejection/audit events go to a job-local sink with no email, session ID, IP, user agent, bearer, or route payload. Reads fail closed on unavailable or malformed stores. The context validates link/reparse-free paths and disjoint roots, but it does not create an OS sandbox: the private child shares the server OS account, so Python-level read-only checks alone do not prevent arbitrary child code from opening the original files for writing. Before bridge integration, either enforce read-only access in the worker sandbox or explicitly accept and test the same-account threat boundary.

There is no existing official parent-verified identity handoff across this subprocess boundary. If avoiding bearer transfer is also required, it needs a separately reviewed server-to-worker capability API with a defined trust and revocation model; neither `workspace.use_caller()` nor the MCP-only `auth.use_agent_user()` supplies that. The current bridge passes the genuine bearer in its JSON stdin payload. `coupled_propeller_s1_process.run_private_process` spools stdin through an anonymous/file-backed `TemporaryFile` under the private attempt root and closes the parent handle after spawning; the token is not added to the job record, checkpoint, result, or logged command, but it is plaintext in the transient input and child memory and should not be described as guaranteed never to touch storage. Current bridge auth readback occurs before and after each canonical solve; with a live read-only provider, a revocation observed during a solve would invalidate that attempt after its raw response is preserved, while cancellation remains the separate mechanism for stopping an in-flight process. Add tests for live revocation/disablement between attempts, read-only behavior (including reject and Google-token paths), no auth-store copies or writes, job-local engineering workspace binding, unchanged normal route guards, and absence of token/store data in all persisted artifacts before enabling public admission.

### Environment-secret bridge binding proposal (provider mode implemented offline only)

Because the actual installed source kind is `environment`, the smallest no-copy bridge path that preserves current HS256 route guards is for trusted server startup to classify the source before child config redirection, then pass the already-configured `AUTH_SECRET` only in the private child process environment while the provider rereads startup-derived users/session files. The provider now has this explicit mode: it reads only the inherited `AUTH_SECRET`, refuses missing/empty values and source-mode mismatches, rereads the variable per verification so rotation invalidates an old token, and retains the private restrictions on token issuance, source-store writes, touch, renewal, and session validation. `configured_process_auth_source()` classifies environment mode before requiring a `.auth_secret` file, while still requiring the configured config, users, and session paths to be real link-free files under the same root. `use_file_backed_auth()` remains file-only. This mode is still not wired into the bridge. Future bridge integration must inherit the value only in its own canonical child environment; never place it in request/job JSON, stdin, command arguments, files, manifests, checkpoints, results, or logs, and do not create another token or synthetic principal. Passing this variable grants child code direct access to the signing key and could let it sign tokens outside guarded helpers; it is a credential exposure/authority expansion even though parent and child share the server OS account. Do not describe this as an OS sandbox or least-privilege boundary. A service/capability would reduce key exposure but requires a new authenticated verification channel and defined revocation/availability semantics. No secret was read or transferred while implementing this offline provider mode, and no production bridge support is claimed.

## Queue, status, result, and cancellation

Use `motor_ai_sim.jobs` as the sole scheduler. The current `/api/coupled/run` pattern uses `_JOBS.queued`, `Priority.DUTY`, and a server-generated run ID. A new route may use that decorator or the equivalent `run_job` closure, but it must not start an unmanaged thread or child before queue admission. Record only safe summary fields in the queue `JobRecord.body`; bearer, copied auth material, full body, raw solver output, and private paths stay out of `.jobs.json`.

Expose the solve through a new authenticated user-tier route, without changing `/api/coupled/continuous_rating`. Return the queue’s existing `202` payload/run ID when asynchronous admission is active. Reuse `GET /api/jobs/{run_id}` for queue state and progress metadata, and `POST /api/jobs/{run_id}/cancel` for cancellation: that cancel route calls `_JOBS.cancel_run` and enforces owner/admin access. Add a separate result-read operation only if needed; it must authenticate and compare the queue record’s owner to the caller before reading the private result store. The generic job status API treats a run ID as an opaque nonce and is not an authorization boundary for disclosing full S1 results.

Bind the job cancellation predicate to both `PropellerS1Job` and `PrivateCoupledBridge`. Check it before every current/RPM callback. The bridge’s `run_private_process` polls while the canonical child is running and terminates/reaps only its own process group; preserve the incomplete attempt and raw checkpoint as cancelled evidence. A cancel must not turn into a verified physical limit or silently launch the next sample. Use global canonical-call and RPM-evaluation budgets in addition to the private child timeout. Current defaults include `QUEUE_WORKERS` or roughly CPU-count/4, a two-job field lane, one running non-field job per workspace when workspaces are enabled, and a private bridge timeout of 1800 seconds; a new job is ordinary DUTY priority and must respect the configured queue rather than raising concurrency.

Store the immutable result through `PrivateResultStore` under the private job root, keyed by the server run ID and verified build identity. The result reader should accept a requested identity digest only as a comparison key, never as proof. Read the owner-scoped job record first, then validate the private result schema, state, result digest, and identity against the admitted server-side identity. Keep raw successful and failed replies with source/build hashes for audit, but redact tokens, email-bearing context keys, and private filesystem paths from client JSON.

## Configure consumer and result meaning

Configure should consume a result only when its current authenticated build identity and assigned propeller source/position match the result’s frozen identity. An L12 passport reference may support the selected L20 configuration only when the family selection and die relationship validate; a result for another configuration or propeller must remain a historical result and never switch the loaded build. Do not alter the existing Configurator/continuous-rating fields or change the user’s saved current, geometry, winding, or cooling mode as a side effect of opening a result.

The solver performs a finite declared RPM search on the propeller’s measured domain, requires an exact candidate RPM, exact frozen identity, torque balance, net shaft-power consistency, and all sourced same-point physical/convergence gates. `candidate` means the highest verified point in that sampled/refined interval is bounded by the next verified infeasible point at the requested resolution; it is not a global mathematical maximum or a released continuous rating. `domain_limited` means the upper declared endpoint is still feasible. Unknown convergence, missing evidence, unsupported connection, estimated/extrapolated propeller coefficients, or an unknown region above the candidate leaves the result unresolved. Keep all output publication flags false until a separate, reviewed qualification policy says otherwise.

## No-copy private-auth binding plan

This plan wires the accepted provider only inside the private canonical worker; it does not change normal Configure login or expose a new API. `api.py` currently registers the regular `coupled_router` and does not import `coupled_propeller_s1_private_bridge`; there is no public S1 bridge route. The bridge module intentionally lazy-imports route/auth modules inside the child. Keep that shape.

1. In the trusted supervisor process, before constructing the child environment and before the child receives its trial `MOTOR_AI_SIM_CONFIG`, call `private_auth_context.configured_process_auth_source()`. It derives the auth root from already-imported `config.DEFAULT_CONFIG_PATH`, `users._USERS_FILE`, `users._SECRET_FILE`, and `sessions._SESSIONS_FILE`; retain only the returned path and classified `file`/`environment` kind in in-memory supervisor state for this invocation. Never accept either value from `PrivateJob`, API request, JSON stdin, a manifest, or a client-controlled environment map. Refuse if config/user/session stores are missing, linked, outside the same configured root, or the source cannot be classified.

2. `_dispatch_and_envelope()` is the current parent spawn seam: it creates the JSON stdin payload, builds a small child environment, and calls `run_private_process()`. Keep the original bearer in the existing transient stdin contract for unchanged auth guards; do not add auth root, source kind, or secret to that JSON. Add the already-classified root/kind only to the trusted child environment (for example, `MOTOR_AI_SIM_PRIVATE_AUTH_ROOT` and `MOTOR_AI_SIM_PRIVATE_AUTH_SOURCE`). For `environment`, inherit the supervisor’s already-present `AUTH_SECRET` into only this child’s environment; if it has disappeared/emptied since classification, refuse before spawn. For `file`, explicitly omit `AUTH_SECRET`. Do not put key bytes or hashes in command args, files, environment dumps, logs, manifests, queue records, checkpoints, or results. Treat the child environment transfer as direct access to a signing credential, not as an OS sandbox or a least-privilege boundary.

3. In `main()`/`_worker()`, after stdlib `_worker_admission()` has validated job and attempt paths but before `_verify_actual_propeller_point()`, `_resolve_runtime_identity()`, or any lazy route/auth imports, enter `use_private_auth()` using the trusted environment root/source plus the validated job root and attempt root. Keep the context active across authenticated pre-readback, `_invoke_canonical_run()`/unchanged `coupled._run`, mechanical/PWM capture, post-readback, and result-envelope creation. The context manager's `finally` reset must cover normal completion, refusal, solver error, and cancellation. `users.verify_token()` then reads the current server user record, token signing source, and matching active session; missing SID, missing/foreign/mismatched session, disabled/deleted user, revocation, expiry, unreadable files, or invalid signature must refuse before run or invalidate the attempt on post-readback. No session creation, revocation, touch, renewal, user linking, or role auto-provisioning occurs.

4. Replace `_bind_private_auth_storage()`'s current requirement that imported user/secret/session paths resolve to `workspace/users.json`, `workspace/.auth_secret`, and `workspace/.sessions.json`. It should continue to assert that `config.DEFAULT_CONFIG_PATH` is the per-attempt trial config, but delegate auth reads to the already-active context and let `sessions.record_event()` write only the attempt-local redacted sink. Do not point `sessions._EVENTS_FILE` back to the installation-wide auth log. The `workspace.use_workspace()` and `workspace.use_caller()` bindings remain necessary for ordinary account/family reads and are separate from auth-store selection.

5. Migrate the private job-input schema before using no-copy auth. `_REQUIRED_CONTEXT_FILES` currently requires `workspace/users.json` and `workspace/.auth_secret`, while `_bind_private_auth_storage()` also insists on `.sessions.json` being copied beside the trial config. Remove those auth stores from the snapshot copier, private input manifest, required-file list, `file_hashes`, and trial workspace clone; do not include them in runtime identities or result provenance. Keep `.user_prefs.json`, `.family_context.json`, saved die/config/duty, materials, and engineering inputs in the workspace as needed for exact build resolution. Bump the private-job marker/worker schema (currently kind `propeller-s1-private-job`) and refuse legacy v1 jobs rather than silently reusing manifests that contain copied credentials. Rebuild such jobs from non-auth engineering inputs; no migration should copy or reclassify an old auth-store snapshot as trusted live state.

6. Preserve the child’s existing authority checks under the active provider. `_resolve_authenticated_context()` already calls `auth.resolve_user_detail()`, checks caller identity against the frozen owner, compares `account.get_last_motor()` to expected selection, and compares `family._read_ctx()` to die/config/duty. `_resolve_coupled_runtime_inputs()` uses `propeller_cooling_context_issue()` and `get_cooling_options()` to verify the selected assigned propeller and `propeller_air` allowance. All checks must run inside the auth context; missing/revoked session or inactive/mismatched family must fail before `_run`, and an unassigned or unsupported propeller must remain a hard refusal. Preserve same-family reference identity and existing propeller source/config assignment rules; do not broaden the allowlist or substitute another assignment.

Required no-solver regressions before any bridge use: parent-side source classification happens before trial-config selection and never puts key contents in the payload; `file` and `environment` child environment construction is source-specific; environment disappearance/rotation fails closed; no auth store is copied or appears in private manifests; malformed/missing/no-SID/foreign/expired/revoked/disabled/deleted sessions reject; revocation/disablement between pre- and post-readback invalidates the attempt; `_run` callback and post-readback observe an active provider and context restoration occurs on every exit; account/family/reference/propeller allowlist mismatch refuses; no fake key/token appears in job files, logs, results, or events; normal no-context auth/session and Configure login behavior remains unchanged. Existing `test_private_auth_context.py` covers the provider in isolation; bridge-side tests must additionally exercise `_dispatch_and_envelope`, stdlib `_worker_admission`, `_worker` context lifetime, and actual allowlist/auth readbacks without invoking FEM. No public route or production readiness follows from passing these tests alone.
