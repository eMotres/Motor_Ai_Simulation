# eMotres MCP server: Stage 1 (read-only) + Stage 2 (OAuth 2.1) + Stage 3 (drafts, simulate), 2026-09-28

The app moved to **aerostator.com** on 2026-09-28 (emotres.com is now the
marketing site). External AI agents (Claude Desktop, Claude Code, claude.ai and
ChatGPT connectors) reach the
eMotres catalog and saved simulation results at **`https://aerostator.com/mcp`**
through the Model Context Protocol. Stage 1 is read-only. It runs no solver
and exports no geometry.

## Architecture

- Uses the official MCP Python SDK (`mcp==2.2.0`, `MCPServer`) with the
  **streamable HTTP** transport in **stateless + JSON-response** mode. Each POST
  is one self-contained JSON-RPC exchange, so there are no SSE streams, no
  session affinity and no special nginx buffering.
- **Where it runs:** inside the FastAPI API process, so it uses the same
  stores and the same permission code as the web. It is not a separate
  service. `motor_ai_sim.mcp_app.McpGate` is added as the **outermost** ASGI
  middleware and takes `/mcp` before the tier gate, the workspace resolver and
  CORS see it. Those layers understand session tokens, and an agent key is not
  a session token. We chose this over a separate ASGI app because a second
  process would need its own copy of the catalog/workspace/grant logic, and two
  copies of an access rule drift apart. nginx adds only `location = /mcp`
  (`deploy/nginx.conf`). The API container and compose file are unchanged.
- McpGate does this for every request:
  1. **Auth:** checks `Authorization: Bearer emk_<id>_<secret>`. On failure it
     returns 401 with `WWW-Authenticate` and a `reason` (`malformed`,
     `unknown_key`, `revoked` or `disabled`). **Since 2026-09-29 a request
     with no `Authorization` header is the anonymous tier:** it may use the
     public discovery tools and the guide only (fail-closed allow-list); any
     other call gets 401 with a structured JSON-RPC error. See
     [MCP_DISCOVERY.md](MCP_DISCOVERY.md) for the tier, the error contract
     and sign-up through the OAuth window.
  2. **Scope:** on `tools/call`, the tool's scope must be on the key.
     Otherwise it returns 403 (JSON-RPC error -32001, `insufficient_scope`,
     `required_action: grant_scope`). `tools/list` shows the public tools
     plus the tools the key's scopes allow.
  3. **Quota:** on `tools/call` only, it counts per key per minute and per UTC
     day (anonymous: every request, per client IP). Over the limit it returns
     **429 with `Retry-After`**.
  4. **Audit:** it writes one JSONL line per tool call (and per auth
     failure): time, user, key id, tool, args summary (≤300 chars), status.
     The file is `config/mcp_audit.jsonl`, next to `users.json`.
- The tools run as the key's owner. `auth.use_agent_user` makes every
  in-process check answer exactly as that owner's own web session would:
  `motor_access.catalog_access`, the per-user die grants,
  `routes.family.tree`, and the workspace layers (own / published / shared).
  `list_machines` calls the **same `family.tree()`** the Motors tab calls.
- Data leaves through a **whitelist**. `mcp_tools.GEOMETRY_DENYLIST` is also
  checked on every answer before it is returned: no stator/rotor dimensions,
  no winding geometry, no thumbnails/SVG, no build signatures and no B-H
  curves. A machine is described only by outer diameter, active (stack)
  length, mass, slot/pole count, material names, ratings, losses and
  temperatures.

## How an owner creates a key

1. Sign in on aerostator.com, click the avatar, then **Access for agents**.
2. Enter a name (for example "Claude Desktop"), tick the scopes
   (`catalog:read`, `machines:read`) and click **Create key**.
3. Copy the `emk_…` token. It is shown **once**. Only its SHA-256 is stored
   (`config/agent_keys.json`).
4. The same dialog lists your keys with their scopes, creation date and last
   use (updated at most once a minute). **Revoke** takes effect on the next
   call. When an account is disabled, all its keys stop working.

API: `GET/POST /api/agent_keys`, `DELETE /api/agent_keys/{id}`, and
`GET /api/agent_keys/audit` (your own last calls). Each account can have at
most 10 active keys.

```bash
claude mcp add --transport http emotres https://aerostator.com/mcp \
  --header "Authorization: Bearer emk_XXXXXXXX_YYYYYYYY"
```

bridge (it needs Node.js):

```json
{
  "mcpServers": {
    "emotres": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://aerostator.com/mcp",
               "--header", "Authorization:${EMOTRES_KEY}"],
      "env": { "EMOTRES_KEY": "Bearer emk_XXXXXXXX_YYYYYYYY" }
    }
  }

```

**claude.ai custom connector (OAuth, Stage 2).** Needs a Pro/Max/Team/Enterprise
plan (on Team/Enterprise an owner adds it for the organisation).

1. claude.ai -> **Settings -> Connectors -> Add custom connector**.
2. Name `eMotres`, URL `https://aerostator.com/mcp`. Leave the advanced OAuth
   client ID/secret empty (the connector registers itself, RFC 7591). **Add**.
3. Click **Connect**. A tab opens on aerostator.com: sign in if asked, check
   the app name and scopes, click **Allow**. The tab returns to claude.ai.
4. In a chat, enable the connector in the tools menu ("Search and tools").

The same connector then also works in Claude Desktop and the Claude mobile apps.

**ChatGPT connector (OAuth, Stage 2).** Needs developer mode (Settings ->
Apps & Connectors -> Advanced settings -> Developer mode; on Business/Enterprise
an admin must allow it).

1. ChatGPT -> **Settings -> Apps & Connectors -> Create** (or "Add custom connector").
2. Name `eMotres`, MCP server URL `https://aerostator.com/mcp`,
   Authentication **OAuth** (dynamic registration; no client ID needed),
   tick "I trust this application", **Create**.
3. ChatGPT opens aerostator.com: sign in, **Allow**.
4. In a chat, pick the connector from the **+ -> Developer mode / tools** menu.

Both connected apps appear under **Access for agents -> Connected apps**, where
**Disconnect** revokes them at once.

## Stage 2: OAuth 2.1 (MCP authorization spec)

The app is both the protected resource and the authorization server; the login
is the existing self-hosted one (Google / e-mail + password).

| endpoint | spec | notes |
|---|---|---|
| `GET /.well-known/oauth-protected-resource` (+ `/mcp` suffix) | RFC 9728 | `resource` = `https://aerostator.com/mcp`, `authorization_servers` = `https://aerostator.com` |
| `GET /.well-known/oauth-authorization-server` | RFC 8414 | also served at `/.well-known/openid-configuration` for clients that only try that |
| `POST /oauth/register` | RFC 7591 | open dynamic registration; public clients (`none`) or `client_secret_post/basic`; at most 500 clients (oldest idle one dropped) |
| `GET /oauth/authorize` | OAuth 2.1 | code + **PKCE S256 only**; `redirect_uri` exact string match; bad client/URI -> 400 page, other errors redirected back; then 302 to the web consent page `/agent-consent?request=…` |
| `POST /oauth/token` | OAuth 2.1 | `authorization_code` (code single-use, 5 min, burnt by a failed attempt too) and `refresh_token` |
| `POST /oauth/revoke` | RFC 7009 | either token revokes the grant |

- **Redirect URIs:** https only; `http` only for `localhost`, `127.0.0.1`, `[::1]`; no fragment.
- **Tokens:** access `emo_<grant>_<secret>` lives 1 h; refresh `emr_<grant>_<secret>`
  lives 30 days and **rotates** on every use. Replaying a rotated refresh token
  revokes the whole grant (theft detection). Only SHA-256 hashes are stored,
  in `config/oauth_grants.json` next to `agent_keys.json`. Refresh can narrow
  scopes, never widen them.
- **Consent:** `/agent-consent` in the SPA (`web/src/components/auth/OAuthConsent.tsx`):
  the signed-in user sees the client name, return host and scopes
  (`catalog:read`, `machines:read`) and clicks Allow / Deny.
  API: `GET/POST /api/oauth/requests/{id}` (session required).
- **Resource server:** McpGate takes `Bearer emk_…` (keys, unchanged) or
  `Bearer emo_…`. Both become the same `Principal`; OAuth has `kind="oauth"` and
  `credential_id` = grant id, so scope checks, quotas (per grant) and the audit
  log are the same as for keys. A 401 carries
  `WWW-Authenticate: Bearer resource_metadata="https://aerostator.com/.well-known/oauth-protected-resource/mcp", scope="…"`
  (plus `error="invalid_token"` for a bad/expired token); a scope refusal is
  403 with `error="insufficient_scope"` and `scope` = held + missing scopes.
  The JSON-RPC body carries `error.data` with `required_action` and a
  `user_message` (contract in [MCP_DISCOVERY.md](MCP_DISCOVERY.md)).
- **Sign-up:** the consent page offers Sign in and Create account; the
  confirmation mail returns to the same pending authorization
  ([MCP_DISCOVERY.md](MCP_DISCOVERY.md) "Sign-up").
- **Owner view:** "Access for agents" lists **Connected apps** next to keys
  (`GET /api/oauth/grants`, `DELETE /api/oauth/grants/{id}` = disconnect).
- **nginx:** `deploy/nginx.conf` proxies `/.well-known/` and `/oauth/` to the
  API; `/agent-consent` stays with the SPA. The host nginx proxies everything
  to the stack (if it answers certbot's `/.well-known/acme-challenge/` itself,
  that location stays in front and is unaffected).
- **Env:** `PUBLIC_BASE_URL` (default `https://aerostator.com`) sets the issuer
  and the resource URL.

Files: `src/motor_ai_sim/oauth.py`, `src/motor_ai_sim/routes/oauth.py`,
`tests/test_mcp_oauth.py`.

## Stage-1 tools (read-only, `readOnlyHint: true`; Stage-3 tools are listed in their section)

| tool | scope | what it returns |
|---|---|---|
| `list_catalog(kind, query?)` | catalog:read | Entries of kind `magnets`, `steels`, `wires`, `bearings`, `devices` or `dies`, with key specs in unit-named fields plus a `provenance` block (source, datasheet, curves present). Dies are only those this account can see. |
| `get_catalog_entry(kind, id)` | catalog:read | One entry. |
| `list_machines()` | machines:read | Own, published and granted machines: die, config, ownership, OD/active length/mass, slots/poles, materials, DC-bus voltages, and per duty `torque_nm`, `power_kw`, `speed_rpm`, `efficiency_pct`, `line_voltage_peak_v`, `mass_kg`. |
| `get_machine_performance(die, config, duty)` | machines:read | Operating point, loss split (core/copper/solid/mechanical W), temperatures (coil/magnet/bearing °C, cooling), continuous rating, time to limit, KV, ripple, duty cycle. A machine that is not visible gets the same "not found" as one that does not exist. |
| `check_fit(torque_nm, speed_rpm, voltage_v?, max_diameter_mm?, max_length_mm?, max_mass_kg?, cooling?, limit?)` | machines:read | Duties that deliver at least `torque_nm` at `speed_rpm` or faster, with peak line voltage ≤ `voltage_v` (DC bus) and OD, active length and mass within the limits. Results come with margins in %. Ranking: fewest unverified checks, then lightest, then most efficient. Rejected duties are listed with reasons. |

Resource: `emotres://guide`, a short usage guide in Markdown.

Quotas are counted in process memory, which fits the single API process on the
server. A restart resets the counters. Stage 3 moves them to the job-queue
store.

## Stage 3: draft designs + simulations through the queue (2026-09-28)

The owner's picture: *the engineer tells his agent "compute me such a motor";
the agent logs in through MCP and does the calculations; when something is
missing it asks the engineer; afterwards a simplified version of the motor is
in Configure where the engineer turns the knobs himself.*  The user and his
agent are **one identity and one workspace**: an agent key / OAuth grant is a
delegated credential of the user, and everything the agent creates is the
user's — labelled with the agent that made it.

### Scopes

| scope | allows | default on a new key |
|---|---|---|
| `catalog:read` | Stage-1 catalog tools | yes |
| `machines:read` | Stage-1 machine tools, `get_design`, `get_design_result`, `open_in_configure` | yes |
| `designs:write` | `start_design` — create DRAFT machines in the user's workspace | no, tick it |
| `simulate` | `simulate`, `get_job` — queue solves of drafts; daily quota | no, tick it |

The key dialog and the OAuth consent page show one line per scope
(`agent_keys.SCOPE_DESCRIPTIONS`).  On the consent page the owner can **untick**
scopes; the grant then carries only the ticked ones (`oauth.decide(..., scopes)`,
subset only).  `duties:write` (overwrite a saved duty) does not exist yet.

### Explicit addressing — the rule

Agent tools **never read or write the user's active context** (the loaded
`motor_config.yaml`, `.family_context.json`, the open tabs).  Every call names
`die/config/duty` or a `design_id`.  An agent's writes are **drafts** only:

- stored in the user's workspace: `<ws>/agent_designs/<design_id>/design.json`,
  with `created_by: {kind: agent, client_name, credential_id}`;
- simulated in the draft's **own sandbox workspace**
  (`<draft>/sandbox/motor_config.yaml`, built from the base die/config/duty +
  the draft parameters; the user's config is only *read* as a template).  The
  solver's per-workspace caches, run stores and "last result" files therefore
  land beside the draft.  EM runs are also wrapped in `run_recording.no_record()`.
  This is also what makes the coupled pre-flight pass honestly: the sandbox
  config holds the draft's speed and connection, so the thermal half looks up
  the same machine the EM half solved (incident 2026-09-27: a duty load
  overwrote a die — never again through an agent);
- visible in the web (Motors -> **Agent drafts**, badge 🤖 + client name),
  **revertible** to exactly what the agent created, and **deletable**.

Tests assert the live config, the context file and every die file are
byte-identical after `start_design` + `simulate`, and that the stubbed solver
was called inside the sandbox workspace.

### Tools

| tool | scope | what it does |
|---|---|---|
| `start_design(requirements, base?, name?)` | designs:write | Validates loudly. Returns `status: needs_input` with `needs_input: [{field, why, options\|range}]` when an essential is missing or contradictory (torque or power, rated speed, DC bus, cooling, duty; power vs torque x speed off by > 5 %; max speed < rated). Plainly wrong values (negative, unknown option, unknown field) are tool errors. Otherwise it ranks every saved duty the user may see (the same visibility as `check_fit`) scaled to the requirements and creates a draft from the best one; `status: no_fit` explains what blocked it and asks which limit may move. |
| `get_design(design_id)` | machines:read | The draft: requirements, assumptions, starting point + why, parameters, estimate, warnings, alternatives, runs. |
| `simulate(design_id, what, steps?)` | simulate | `what`: `em` (transient), `thermal` (one EM pass + one thermal solve = coupled with `max_iter 1`), `coupled` (EM <-> thermal loop). Submits to the **same queue the web uses** (`jobs.queue()`, kind `agent.<what>`, priority DUTY, the user's `ws_id` and owner, `body.agent` = the client), non-blocking; returns `job_id` at once. The user's own runs keep their normal queue order. |
| `get_job(job_id)` | simulate | state, queue position, progress (step/total/%), ETA, elapsed, error — the web progress bar's data. Only the account's own jobs. |
| `get_design_result(design_id)` | machines:read | Per `what`: torque, power, efficiency at the shaft (+ electromagnetic), line voltage peak, current, ripple, loss split (copper/core/magnets/solid/mechanical/total W), temperatures (coil/magnet/bearing degC), convergence, limits, mass (scaled estimate), and `requirement_checks` (torque met, voltage fits bus). Whitelisted and re-checked against `GEOMETRY_DENYLIST`. |
| `open_in_configure(design_id)` | machines:read | `https://aerostator.com/?tab=configure&design=<id>` |

**Scaling rules (no new laminations in this stage).**  From a saved duty
(T0, n0, I0, V0 line-peak, L0 stack): stack factor `kL = T/T0` clamped to
0.5–2.0 and to `max_length_mm`; the rest by current `kI = T/(T0 kL)`, limited
by current-density factor 1.3 (S1), 1.8 (S2/S3), 2.2 (peak) — at constant slot
fill J scales with `kI` only; winding: the largest series-turns factor
`kT <= 0.9 Vdc / (V0 kL n/n0)` (0.25–2.0) realised with an integer number of
turns and a parallel-path count dividing the coils per phase; phase current
`I0 kI / kT`; mass `m0 kL` (estimate).  Speeds above 1.2x the fastest verified
duty of that machine, generator-characterised bases and field weakening at max
speed come back as **warnings**.  Ranking: least stretch
(`|ln kL| + 1.5 |ln kI| + 0.5 |ln n/n0|`) plus 0.3 per warning.  Turn counts
and wire sizes stay internal (`design.internal`, never returned by MCP).

**Elicitation.**  The server runs stateless JSON-response streamable HTTP
(Stage 1), where a server-to-client `elicitation/create` request has no open
stream to travel on, so MCP elicitation is not used.  The conversational
pattern is carried by the `needs_input` answer instead and stated in the tool
descriptions and the guide resource: *do not guess — ask the engineer each
listed field, then call again*.

### Quotas

- Per-key rate limits as Stage 1 (`MCP_RATE_PER_MIN`, `MCP_RATE_PER_DAY`).
- **Simulations per account per UTC day:** `MCP_SIMULATE_PER_DAY` (default 5),
  counted from the job queue's own records (`body.agent` jobs queued since
  midnight in the user's `.jobs.json` + memory), so a restart does not reset
  it and every key/grant of the account shares it.  Unlimited for admin
  accounts (`ADMIN_EMAILS` — the owner) and for `MCP_SIMULATE_UNLIMITED`
  (comma-separated e-mails).  Over the limit McpGate answers **429 +
  Retry-After** (seconds to UTC midnight) before the tool runs.

### Web

- **Motors tab -> Agent drafts** (`AgentWorkPanel.tsx`): one row per draft
  (🤖 client name, base machine, L / I / rpm, FEM torque when simulated),
  **Configure**, **Revert** (enabled once edited), **Delete**; below it
  **My runs** from `GET /api/jobs`, agent jobs badged 🤖, **Stop** on queued /
  running ones (`POST /api/jobs/{id}/cancel`, owner-checked as before).
- **Configure**: `?tab=configure&design=<id>` (or the Configure button) shows
  a banner "Agent draft … by …"; **Open** loads the draft into the
  client-side tuner (reference passport = the catalog card of the base
  machine, knobs = stack / turns / connection / current / speed); nothing on
  the server's open machine changes.  **Save to draft** PATCHes the tuned
  values back (`PATCH /api/agent_designs/{id}`; results are cleared because
  they describe the old machine).
- **Access for agents**: the four scopes with their descriptions and the
  simulations/day of this account; new keys default to read-only.
- API: `GET /api/agent_designs`, `GET/PATCH/DELETE /api/agent_designs/{id}`,
  `POST /api/agent_designs/{id}/revert` (`routes/agent_designs.py`).

### Example conversation

> **Engineer:** Compute me a motor: 0.5 N·m at 10 000 rpm for a 48 V drone
> gimbal, as small as possible.
>
> **Agent** -> `start_design({torque_nm: 0.5, speed_rpm: 10000, dc_bus_v: 48})`
> <- `status: needs_input` — `cooling` (air | liquid | robotics: "the
> continuous current, hence the size, depends on how the heat leaves the
> machine"), `duty` (S1 | S2 | S3 | peak).
>
> **Agent:** How is it cooled, and is 0.5 N·m continuous or a short peak?
>
> **Engineer:** Still air, continuous.
>
> **Agent** -> `start_design({..., cooling: "air", duty: "S1"})` <- draft
> `d-2c8f5c59c938`: from *CIANO14 40_12 / L12 / rated* (0.6 N·m at 13 000
> rpm, OD 40 mm); stack 12 -> 10 mm; current density x1.00; series turns x2
> (2S) so ~22 V peak fits 90 % of the 48 V bus.
> -> `simulate(d-2c8f5c59c938, "coupled")` <- `job_id coupled-…, position 1`
> -> `get_job` … `running 18/40, eta 95 s` … `done`
> -> `get_design_result` <- torque, shaft efficiency, losses, coil / magnet
> temperatures, `requirement_checks: {torque_met: true, voltage_fits_bus: true}`
> -> `open_in_configure` <- `https://aerostator.com/?tab=configure&design=d-2c8f5c59c938`
>
> **Agent:** Here it is — 40 mm OD, 10 mm stack, … Open the link to tune
> length and turns yourself; your open machine is not changed.

### Deferred (not in Stage 3)

- New lamination synthesis (a die the catalog does not have) — `start_design`
  answers `no_fit` and asks which limit may move.
- `duties:write` (saving a draft as a real configuration/duty), MCP
  elicitation (needs a stateful transport).
- Drafts carry the base machine's bearings/windage only through the base
  duty's figures: the sandbox has no catalog context, so `mechanical_losses_included`
  is usually false and the shaft efficiency then excludes bearings/windage.
- User-custom materials are not copied into the sandbox (catalog materials only).
- Fair-use limit in solver-minutes (today: runs per day).
