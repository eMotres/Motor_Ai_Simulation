# Exact-build admission data audit for propeller S1 jobs

**Status:** read-only source audit of `scratch_s1_20261006/default40-release`; no application changes, API calls, or FEM runs.  
**Purpose:** identify where a queued propeller operating-point job can get an exact saved-build snapshot, what the existing fields do and do not prove, and how to isolate compute from the loaded editor.

### Read-only versus state-changing seams

`GET /api/family/context`, `GET /api/me/last_motor`, `GET /api/catalog/{id}/configure_context`, `GET /api/propellers/cooling-options`, and `GET /api/propellers/{id}` are read paths. Internally, the resolver can read family YAML and shared catalog data without invoking `family.activate()`.

Do **not** call `POST /api/family/activate` or catalog motor load from a job admission/worker. `family.activate()` stamps `.family_context.json`, synchronizes mesh values into the mutable simulation config, and may apply duty geometry when explicitly requested. Catalog `/{motor_id}/load` likewise exists to load a machine into the editor. A queued solver must not alter the current editor or workspace files.

## Recommended minimal admission contract

1. **Resolve the caller and build without mutation.** Use the verified auth subject, validated `last_motor` tuple, active family context tuple, authorized family read layer, exact die/config YAML documents, and named duty. Require all three selectors (last selection, active context, resolved saved docs) to agree on die/config/duty. Require an explicit, accessible `ref_id` that resolves to the same permitted family association (different configuration under that family is valid). Keep it as a separate identity component; establish exact geometry/build identity from the independently resolved selected config and drift-checked current snapshot.
2. **Build a deterministic M0 snapshot.** Reuse `passport_v1.snapshot.machine_snapshot()` for the normalized die+config geometry, winding, material assignment/cards, rated duty, mesh, battery, bearings, part states, and source hashes. Reject if required values or material cards are unresolved, the duty lacks required point/mesh fields, or the actual family source files change while they are being read. Add `ref_id`, opaque owner scope, exact family layer/source revision, controller/drive selection and constraints, normalized Thermal settings/cooling fields, allowed propeller assignment, prop source file bytes/hash, solver source/build identity, and any input not covered by the snapshot builder. Retain each component and its hash in the job; a composite hash without its source values is not enough to explain mismatches.
3. **Compare the active runtime config, then freeze.** Read the current workspace config and live geometry only for a read-only equality check against the fully resolved saved snapshot (geometry, winding, materials/part states, duty operating point, and mesh). Reject any mismatch as unsaved/stale state. Do not auto-save or reload. Enqueue a deep-copied immutable snapshot plus resolved solver kwargs and input hashes; subsequent panel edits must not affect the job.
4. **Use a private worker sandbox.** Create an isolated job workspace/config root and use the existing `workspace.use_workspace()` scope so config, mesh, result caches and per-request stores resolve inside the job sandbox. Populate only the exact frozen motor configuration and required read-only library inputs. The current `material_context.set_request_materials()` only calls `ContextVar.set()` and returns no reset token/context manager. A fresh process per job is the simplest isolation boundary; if a reused worker is introduced, it needs a scoped set/reset seam before setting per-job material context. Use explicit `geo_override`, mesh, temperatures, current/RPM, drive and cooling kwargs derived from the snapshot. Do not share the live user `Workspace` object for a long job, mutate its geometry singleton, call editor load/activate routes, or rely on a late lookup of `.family_context.json`, current config, or panel settings.
5. **Revalidate at publication, not by re-solving in place.** Compare the active saved build/source hashes with the job snapshot before marking a result available. If the build, assigned prop, cooling fields, or source content changed, keep the completed artifact as stale/unqualified and do not match it in Configure. Use a separate immutable job/result store, not passport records, duty results, or editor “last run” caches.

A changed active tab selection during a long solve need not corrupt the frozen solve; it must prevent the result from being offered as current if the latest build identity no longer matches. A future queue/result endpoint must authorize each read against the same opaque owner and exact selected build, not trust a client-supplied hash by itself.

## Existing test seams and focused regression coverage

Useful existing tests include:

- `tests/test_last_motor_preference.py`: required last-motor tuple validation, same-die/different-config reference behavior, invalid/missing access and revocation.
- `tests/test_family_activate_mesh_sync.py`, `tests/test_family_released_context.py`, `tests/test_family_payload_absent_keys.py`: family context and duty mesh behavior. Activation tests are for existing semantics; a new admission test should assert the path does not call activation or write config/context.
- `tests/test_passport_v1.py`: pure snapshot resolver behavior, duty mesh fail-closed rules, material name resolution.
- `tests/test_thermal_propeller_source.py`: current propeller-source guard for owner/last motor/family/allowlist; its current key protects source selection but is intentionally not a full build fingerprint.
- `tests/test_workspace_workers.py`, `tests/test_workspace_state.py`, `tests/test_workspace_layers.py`: workspace context isolation and shared-layer resolution.
- `tests/test_coupled_propeller_source.py`: normal coupled route rejects stale/mismatched propeller context before solver callbacks.

The smallest new no-FEM admission tests should patch solver callbacks to fail if called and assert: exact saved active context enqueues a self-contained snapshot; unsaved config drift, different-family or unresolved reference, missing active duty, changed source file during capture, inaccessible family/prop, missing required mesh/material, stale prop hash, or empty required assembly bound refuses with no callback and no state write. A sandbox test should run two job workspaces concurrently with different frozen configs/material contexts and assert no shared cache/config mutation. Configure result matching should require the current complete identity, not only a family key or passport variant ID.

For an ordinary Thermal/Configure cooling estimate release, missing rotor structural or bearing limits can be disclosed as unavailable without blocking the cooling estimate. For a claim of maximum continuous propeller-loaded assembly speed, that candidate remains unqualified until required bearing, rotor/sleeve, thermal, controller and pack bounds are resolved and explicitly pass at the same matched operating point.

**Audit boundary:** this note identifies data paths and admission contracts only. It does not create a job, alter the solver/search module, access the live service, or validate a maximum-speed result.
