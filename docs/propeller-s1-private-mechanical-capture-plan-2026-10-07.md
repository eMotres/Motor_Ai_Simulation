# Private coupled mechanical-result capture plan

## Recommendation

Capture the rotor-stress hook result at the point where the existing coupled path already computes it. In a dedicated, authenticated private child only, wrap `motor_ai_sim.routes.mechanical.run_rotor_stress_at` immediately before invoking the unchanged canonical `routes.coupled._run`. The wrapper records the actual `temps` and keyword arguments, calls the original function once, retains its complete returned mapping and returns that same mapping unchanged. Do not call the mechanical route again to fill in the result: `_mechanical_step` has already reduced the full mapping to a compact `coupling.mechanical` block by then.

The coupled call is opt-in (`body.mechanical is True`). `_mechanical_step(body, field, authorization, rpm, torque_nm)` selects each part temperature from the converged same-run thermal field using `_bulk_temp` (average when present, otherwise maximum), rounds it to 0.01 °C, and passes the run RPM and EM-derived shaft torque to the hook. If the toggle is off, no thermal field exists, the hook is skipped, or the wrapper does not observe exactly one callback, the mechanical evidence is unknown. Never repair a missing capture by starting another solve.

This hook wrapper is the least invasive capture point: it observes the actual route call and its full result without replacing solver functions or changing shared routes. Install it only in the one-job child after admission and source-hash checks; restore the exact original callable in `finally`. The callback should retain canonical-JSON-safe copies of the original arguments and result, their hashes, and a count. Do not persist authorization, email-bearing context keys, or tokens in this record. The identity may carry only the existing opaque/hash representation; the raw context key remains transient for the route's own guard.

## Effective inputs that must be frozen and read back

The callback's explicit arguments are not the complete mechanical request. `run_rotor_stress_at` resolves the user's authenticated Mechanical-panel settings, request material context, geometry context, and route defaults before it calls `rotor_stress`. Freeze and independently reconstruct the normalized effective values from that same private runtime, before and after `_run`:

| Input | Actual source/resolution |
|---|---|
| Geometry | Coupled request `geo` if present; otherwise the active private geometry. The mechanical result's `geo_fingerprint` is the final readback. |
| Material assignments | `routes.mechanical._assignments()`: configured assignments merged with request-scoped `material_context.get_request_materials()['assignment']`. |
| Material overrides | `routes.mechanical._override_props()` from the same request-scoped material context. Hash the complete normalized override values and the resolved mechanical material records, not just override keys or material names. |
| Mechanical panel | `routes.mechanical._mech_panel_settings(authorization)` via `routes.panel_settings.get_panel_settings('mechanical', authorization)`. Capture the nonsecret raw panel settings and the normalized effective settings. |
| Effective settings | `cases`, `overspeed_factor`, `interference_mm`, `mesh_size_mm`, `order`, `loads`, `torque_nm`, `contacts`, `lift_off_solves`, `symmetry`, plus the per-part temperatures and geometry above. Route resolution is caller value, then panel value where supported, then explicit route default. For the coupled hook, RPM and torque are supplied by the coupled point; do not take them from panel values. |
| Same-run temperatures | Full coupled response `thermal` field; derive each `rotor_core`/`magnet`/`shaft`/`sleeve` value with the exact `_bulk_temp` rule and 0.01 °C rounding. Verify the hook arguments, full mechanical result thermal block, compact coupled block, and mapper observations all agree. |
| Applied torque | The coupled point's actual EM-scaled torque passed into the hook. The mapper ties it back to the same response's EM summary and `end3d.k_flux`; the mechanics result may report zero applied torque when loads exclude torque. |
| Materials/results | Preserve the actual complete `run_rotor_stress_at` result, including materials, contacts, mesh, case table, per-part averaged stress/factor rows, and geometry fingerprint. Independently resolve and hash actual assignments, override values, and material records under the bound workspace. |

The pure mapper in `coupled_propeller_s1_mechanical_evidence.py` requires the complete unchanged coupled response and full hook result, plus `mechanical_request`, `mechanical_policy`, `source_manifest`, `thermal_observations`, and `run_provenance`. Required provenance binds the actual coupled body hash, full response hash, full mechanical-result hash, effective mechanical-request hash, resolved-material hash, thermal-field hash, identity hash, and exact source hashes for `routes/coupled.py`, `routes/mechanical.py`, `simulation/mechanical/rotor_stress.py`, and `report.py`. The report policy is the sourced `motor_ai_sim.report.SF_ACCEPT` value 2.0. Build these from inspected runtime/source data; never echo a caller-supplied identity as the actual readback or manufacture limit observations.

## Cache and hidden extra-solve behavior

The mechanical route has both the process-local `rotor_stress` cache and persistent `.run_history/mechanical.rotor_stress` storage. The hook currently does not forward a `fresh` parameter to `rotor_stress`, even though the route itself accepts `fresh=True`. Therefore use a new per-attempt private workspace and a fresh child process, with no imported process cache, and ensure the attempt's private `.run_history/mechanical.rotor_stress` has no eligible prior entries before importing the application. Keep the source workspace unchanged. Reject any captured result marked `cached` or `served_from_history`; do not treat an old identical-input result as a same-run solve. Because the route cache key includes assignment names and only override-property keys (not override values), cache isolation is necessary even when a key appears to match.

Set `MECH_LIMIT_SPEED_AUTO=0` in the child environment before importing `routes.mechanical`. The coupled hook runs in recorded jobs, and the default automatic limit-speed path can perform additional stress solves after the primary result. The captured result must be returned before any such extra limit-speed search is enabled; this environment switch avoids that unrelated work without changing solver code.

There is one remaining multiplicity caveat: `rotor_stress` itself can retry with a bonded contact after a separation-contact runaway. That retry occurs inside the one hook callback, and the current hook has no switch to forbid it. A result containing `contact_fallback` must remain unknown unless the exact fallback is separately approved by the mapper. If policy requires proof that only one low-level stress solve occurred (including failed attempts), the hook wrapper alone cannot prove it; add a child-local call counter/guard around the low-level solve or make the route expose the actual attempt count in a separately reviewed change. Do not claim “one stress solve” based only on one `run_rotor_stress_at` callback.

## Child wrapper lifecycle

1. Verify the admitted hashes for coupled/mechanical/rotor-stress/report sources and the original `run_rotor_stress_at` callable before patching. Bind the authenticated caller, selected same-family reference/configuration, request-material context, and private workspace exactly as the admitted run already does.
2. Resolve and hash the effective panel settings, material assignments/overrides, geometry fingerprint, mechanical materials, drive/build identity, and fixed policy source. Refuse if a required value is absent, unresolved, or uses a live/shared workspace.
3. Install a wrapper that increments a private counter, stores a safe copy of the exact `temps` and kwargs, invokes the original callable, stores a safe copy/hash of its complete return value, and returns that same return value. On exception, store only a sanitized failure record and re-raise so the canonical `_mechanical_step` retains its existing failure behavior.
4. Run the unchanged canonical `_run` once. In `finally`, restore the exact original callable regardless of success, cancellation, or exception. Check that the wrapper was called exactly once and that private immutable physics/config/material/panel inputs did not change. Session-touch or other explicitly allow-listed attempt-local auth bookkeeping must remain separate from the frozen physics snapshot.
5. Validate the capture against the returned coupled response and the mapper's exact schema. Require the same thermal field, RPM, EM torque, material/geometry/contact/mesh/settings snapshots, complete result, fresh marker absence, and full provenance. Missing/failed mechanical output or any mismatch yields an unknown gate; no second stress solve is allowed as recovery.

## Safer than cache interception

Intercepting `rotor_stress.cache_get`, reading a history entry, or consulting the Mechanical tab's “last result” is not adequate. Those paths can return a prior result; history payloads can be loaded independently of the current coupled response; and the current mechanical cache key does not include override values. The one-call hook captures the actual result that `_mechanical_step` consumes and preserves its exact relation to the same coupled thermal/EM response. Cache isolation plus rejection of cache markers is required to make that capture fresh.

## Stub-only verification checklist

No FEM or application-server run is needed to test the wrapper boundary. In an isolated test process, replace the original hook with a deterministic fake and exercise the real capture wrapper around a stubbed canonical `_run`:

- successful call: exactly one hook invocation; exact input argument snapshot; returned object is passed through unchanged; full result hash matches; thermal/EM response and mapper gate agree;
- hook skipped, called zero times, or called twice: unknown/refused capture;
- hook raises, returns an invalid/non-JSON result, or reports cache/history markers: sanitized failure or unknown, with no retry;
- source hash or original callable mismatch: reject before `_run`;
- mutation of panel settings, assignments, override values, geometry, contacts, mesh, or material records between pre-read and post-read: reject;
- mapper consistency mutations (thermal average, torque scale, compact rounding, geometry fingerprint, actual material card, stress rows, report policy/source hash): gate becomes unknown;
- restoration: original function object is restored after success, exception, and cancellation;
- isolation: base workspace hashes remain unchanged; only the unique attempt's safe mechanical result/provenance artifact is written.

These checks establish capture software behavior only. They do not qualify a motor, establish an unsourced mechanical limit, or substitute for a subsequently authorized private solver run and independent review.

## Capture-boundary implementation checkpoint

The release checkout now has a child-local capture primitive in `src/motor_ai_sim/coupled_propeller_s1_mechanical_capture.py` and mock-only tests in `tests/test_propeller_s1_mechanical_capture.py`. It does not import application routes itself. A caller must inject the mechanical module and an independent readback function; the helper requires an explicit private-child marker, an attempt-local `MOTOR_AI_SIM_CONFIG` under `MOTOR_AI_SIM_PRIVATE_JOB_ROOT`, no `WORKSPACES_ROOT`, `MECH_LIMIT_SPEED_AUTO=0`, and an admitted source path/hash before it patches the hook. The source hash is checked against both the loaded module bytes and the independent runtime source manifest.

The readback contract separates frozen `invariant` values (panel and normalized settings, material assignments and overrides, geometry fingerprint, resolved materials, and source hashes) from the two pre-run point inputs: candidate RPM and current. Final part temperatures and EM torque are unknown until the coupled run, so they are never expected from admission or pre/post runtime readback. The hook wrapper records the actual finite temperatures and torque together with its actual RPM; the downstream mapper must bind those quantities to the same canonical coupled response. Consumers must call `checkpoint_canonical_response(response)` immediately after `_run` returns and before leaving the capture context, so an exit-time readback failure retains both the canonical response and raw hook result. The wrapper strips authorization from stored kwargs, calls the original callback once and passes its exact return object through, blocks a second callback before invoking it, restores the original callable in all context-manager exits, and retains JSON-safe negative results before validation, rejecting cache/history markers and comparing independent pre/post invariant readbacks. Invalid or unserializable data is recorded with sanitized failure metadata; this helper does not create a qualification gate or populate the mapper envelope.

## Raw rotor-stress key-schema correction

The earlier mechanical-mapper fixture's 40 passing cases did not establish compatibility with the actual raw helper result: it incorrectly normalized the structural `rotor` key to `rotor_core`. The admitted `rotor_stress.py` source has an explicit `PART_ASSIGNMENT_KEY` (`rotor` -> `rotor_core`) and inverse `PART_TEMP_KEY`; full structural `materials`, `cases[*].parts`, `sf_min_per_part`, and limiting-part rows use internal key `rotor`, while `thermal.part_temps_c` uses public key `rotor_core`. The mapper now preserves and hashes that raw shape, uses an explicit one-to-one alias for comparison only, and requires the frozen solver's rotor-stress code hash to equal the accepted source-manifest hash before applying it. Fixture expectations use internal structural material keys and public thermal keys. Added regressions prove raw-result non-mutation, source-shaped keys, collision rejection, and source-hash binding. Focused Python 3.11 run of `tests/test_propeller_s1_mechanical_evidence.py`: **43 passed**. This remains pure/injected evidence mapping; it does not establish a real captured solve or a qualified mechanical result.

## Private bridge integration checkpoint

The release bridge now integrates the capture primitive only for requests with `mechanical: true`. It freezes an independently read mechanical input snapshot into the runtime identity: validated caller-bound panel settings, actual present-part assignments and resolved material records, material overrides, geometry fingerprint, normalized Mechanical settings, and hash-bound source files. The panel settings file must be present and source-hash admitted; malformed or corrupt content is refused rather than replaced by the route's fallback defaults. Nonmechanical identities retain their existing shape and behavior.

After the canonical coupled response is checkpointed, the bridge passes the same-run captured hook result and actual thermal field into the mapper. Only a mapper-consistent pass/fail is converted into source-backed numeric stress-versus-allowable observations for the point consumer; missing or contradictory evidence stays unknown. The response and raw capture remain checkpointed if later identity or mapping validation fails. These changes do not register a public route or claim a qualified result.
